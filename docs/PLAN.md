**为什么这样排**

- **F1 先进入候选版，试用期间只部署修复。** 试用覆盖实际发布的功能集合，便于定位稳定性问题。
- **资源画像从第三批提到 F1。** 越早采集，能积累的历史越多。升级时仍在跑的任务从接管后采样。F2 的参数编辑与任务组会复用画像，静默提醒也共用进程采集。
- **F1 内部先做备注。** 它最小，先把"单独 UPDATE、不进 `SaveJob` 列清单"的写法立起来，2.2 的 `notify_done` 照搬。
- **F2 排在客户端前面。** F2 改的是队列模型（顺序、暂缓、任务组），客户端的总览和托盘都显示队列。和 ROADMAP §1 先做后端的理由一样：接口还在变时做客户端，每次都要跟着改 `packages/core`、两个界面和 Rust 层的轮询。这和 ROADMAP §4 里"定版后回去做客户端"的说法不一致，需要你确认 ❓。
- **F3 只读、不碰调度器。** 哪一批有空档就插进去，排在 F2 后面只是默认位置。
- **F4 不排期。** 命令行提交取决于你会不会从终端或脚本发任务，GPU 保留取决于临时调试的频率（FEATURES 第 5 节）。

## 2. 分支、迁移和部署规则

- **试用期间用发布分支。** F1 和 R1 齐备后从干净提交创建 `release/0.2` 和 `v0.2.0-rc.1`。试用中发现的问题在发布分支修，部署 `rc.2`、`rc.3`……，修完合回 `main`。试用通过后，在最后一个候选版提交上打 `v0.2.0`，构建时显式设置 `VERSION=v0.2.0`，核对 CLI 和 `/api/me`。
- **发布分支尽量不加迁移。** 迁移是按下标追加的列表（`PRAGMA user_version`）。两条分支各加一条，同一个版本号就对应了两份不同的 SQL。修复非加迁移不可时，main 上把这条迁移插到所有 F 迁移的前面，F 的迁移顺延。F 的迁移部署到真机之前都还能挪位置；开发机上 `dev-wsl.sh` 的数据库删掉重建即可（库比程序新时 `store.Open` 会拒绝启动）。部署过的迁移照旧永远不改。
- **F 阶段的迁移顺序**（按这个顺序追加在 `totp_used_steps` 那条之后）：
  1. `jobs.memo`（F1 2.1）
  2. `jobs.profile_json`（F1 4.2）
  3. `jobs.notify_done`（F1 2.2）
  4. `jobs.queue_order`（迁移时设为 id）、`jobs.held`（F2 3.2）
  5. 表 `job_groups`，`jobs.group_id`、`jobs.params_json`（F2 3.4）
- **接口只做加法，`APIVersion` 保持 1**（FEATURES 第 7 节）。每个改动里同步 `packages/core` 的类型和请求函数，`desktop` 保持能编译。
- **哪些能并行。** 几乎每项功能都要改下面这些文件，所以主线一次只做一项：`internal/store/store.go`（迁移和列清单）、`internal/scheduler/`、`internal/notify/notify.go`、`web/src/pages/JobDetail.tsx`、`NewJob.tsx`、`Jobs.tsx`。可以单独开 worktree 和主线同时做的只有三块：2.4 日志搜索（`internal/logs`、日志接口、`LogViewer`）、3.3 的 shell 分词器（只在 `packages/core`）、4.1 的后端（新文件 `internal/api/files.go`）。
- **每个阶段的收尾**沿用 PHASES.md 第 2 节：跑 AGENTS.md 里的全部检查和 `scripts/e2e.sh`，浏览器 1440px 和 390px、深浅两个主题看一遍；接口和配置并入 DEMO.md，命令并入 README，ROADMAP §5 和 FEATURES.md 对应条目标上状态；部署到真机实际用起来，打这一阶段的版本号。

**FEATURES.md 写完之后代码有变化，下面几处以本文为准：**

- **进程身份**。`procfs.JobMarker` 对应 `DANLU_RUN_DIR`，以任务的 `RunDir(id)` 匹配同一实例的进程。
- **进程采集**。Linux 的 `Executor.ProcStats` 读取 `stat` 和 `status`，同时返回 RSS 之和与 D 状态进程数。调度器只读缓存，其他系统通过桩返回采样不可用。
- **扫 `/proc` 放在调度锁外面。** 每个任务都要读所有进程的 `environ`，进程多的服务器上不是毫秒级的事。4.2 每 30 秒扫一次，2.3 发提醒时扫一次，结果缓存起来给锁里用，做法和磁盘采集一样。
- **GPU 归属不用改。** `gpu.Proc.JobID` 现在由 `procfs.JobOf(pid, runRoot)` 算出，只认本实例 `run/` 下的任务，累加器直接用它，别的数据目录的任务自然算外部进程。
- **共用的运行时统计。** Manager 累计 GPU 平均利用率、各卡显存峰值和 RSS 峰值，按采样时间去重，分别记录 GPU 和主机的采样覆盖。每 5 分钟及收尾保存 `profile_json`，重启时从已保存的统计继续累计。日志修改时间和最长输出间隔只在内存里记录。
- **静默告警随任务结束清除。** `silent:<id>` 在收尾时清掉，推送服务不推"已恢复"。danlu 重启时，告警按现有机制从最后一条事件恢复。
- **跑完汇总与暂缓的关系。** FEATURES 2.2 定义"运行中 + 排队 + 启动中归零"时写 `queue_drained`。F2 加上暂缓以后，只剩暂缓任务时算不算跑完，到 3.2 时要定下来（第 5 节）。2.2 实现时把"还有没有能跑的任务"写成一个函数，3.2 只改这一处。写库失败、还在 `pending` 里的任务按它的实际状态计入。
- **备注的显示位置。** 详情页现在在第 212 行把系统写的 `notes` 显示成"备注："（FEATURES 引用的还是第 140 行），改名"运行说明"时以这里为准。
- **日志搜索的两个细节。** Go 这边要自己做 `\r` 折叠（core 里的那份是 TS，给前端渲染用）；返回的偏移取匹配行的行首，这样 `?offset=` 打开时正好从这一行开始。残缺 UTF-8 沿用 `logs.RuneSafe`，已结束任务读到末尾的方式和 `ReadFinal` 一致。

**测试脚本**：`scripts/s0/jobs/` 加一个故意让 DataLoader 死锁的脚本，给 2.3 的真机验证用。

**验收**。本地检查按第 2 节执行。配置 `runtime.silence_alert` 和 `notify.queue_drained` 已并入 README 和 DEMO.md。候选版真机验收按 R1 清单 F 节进行。

**补充和修正**

- **3.3 先做。** 它只改前端和 core，不碰调度器，风险最低；3.4 的"扫描"按钮就长在它的参数行上。core 的单元测试接进现有的测试（CI 已经在跑 core 的 5 项测试）。
- **3.1 的"排队期间修改过"从事件里读。** 详情接口查这个任务有没有 `job_edited` 事件，不另加列。编辑除了拒绝 `pending` 里的任务，也要拒绝 `starting` 里的（占位后、启动前的那段时间）。
- **3.2 的排序要处处一致。** 排队任务的读取、`queue_pos` 和告警里的"队首"都改按 `queue_order, id`，队首取第一个没有暂缓的任务（现在是 `alerts.go` 里直接取 `queued[0]`）。放回队列（`job_requeued`）不碰 `queue_order`，位置自然不变。面板和客户端按服务器给的 `queue_pos` 排，客户端只需保持编译。
- **只剩暂缓任务时算不算跑完** ❓：默认算，发汇总。暂缓是你主动按住的，其他任务跑完了，告诉你一声正好去处理它。
- **3.4 的成员顺序。** 整组在一个事务里插入，`queue_order` 等于各自的 id，所以一组在队列里是挨着的。之后用 3.2 移动单个成员，组就会被拆开，这是允许的；组只是一层归类。
- **3.4 组详情表的资源列**直接用 F1 的资源画像。

**验收**：FEATURES 各节的验收条目，其中 3.4 的 e2e 覆盖了整条链：2×3 扫描 → 第一个快速失败 → 暂停 → 批量替换 → 继续。部署为 `v0.4.0`，用一次真实的学习率扫描。
