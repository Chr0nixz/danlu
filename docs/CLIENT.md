# Danlu 桌面客户端 · 方案 v0.8

> 常驻托盘的多服务器控制台，外加服务器运维工具。
> 状态：C1（打通骨架）和 C2（第一版）已完成，下一步是 C3。带 ❓ 的是待确认项。变更记录见文末。

## 1. 定位

- **客户端**：在一台电脑上同时管理所有服务器：看总览、操作任务、部署和维护 danlu。先做 Windows，以后支持 macOS。
- **服务器自带的 Web 面板**：保留，给没装客户端的设备（手机）用，也是客户端出问题时的兜底。两者界面完全独立，只共享接口和不带样式的逻辑。
- **写代码、同步代码的流程不变**：仍然自己 rsync/scp 到各台服务器，客户端不碰本地代码。

## 3. 不做什么

- 不碰本地代码：不上传快照、不把代码取回本地、不和本地代码做 diff。
- 不自动选服务器：各台的路径和 conda 环境名不一样，提交时必须先选服务器。
- 不做跨任务对比。
- 暂不支持 macOS 和 Linux 桌面。但设计和实现都不能绑死 Windows：凭据、SSH、托盘、快捷键、窗口外框都要有 macOS 上的对应做法（第 5、9 节）。
- 不做节点之间的组网：多台的汇总由客户端完成，服务器之间互不认识（见第 10 节）。

## 4. 架构

```
 ┌──────────── danlu 桌面客户端（Tauri 2，先做 Windows）────────────┐
 │ React 界面：总览 / 历史 / 服务器 / 设置 / 托盘浮窗                 │
 │        │ invoke、Channel                                          │
 │ Rust 层：服务器列表、令牌（系统凭据库）、固定证书的 HTTPS、         │
 │         日志流转发、托盘和系统通知、调用系统的 ssh / scp            │
 └────────┬───────────────────────────────────┬─────────────────────┘
          │ HTTPS：设备令牌 + CA 指纹固定       │ SSH：系统自带的 OpenSSH
          ▼                                   ▼
   gpu1 / gpu2 / gpu3 上的 danlu         同一批服务器：部署、升级、体检、改配置
```

- **日常数据走 HTTPS 直连**：GPU、任务、日志、快照。每台服务器的请求都由 Rust 发出，只信任这台服务器自己的本地 CA；界面不直接访问服务器。
- **运维走 SSH**：每个运维动作都是执行一条 danlu 子命令。直接调用系统自带的 OpenSSH（Windows 上是 `ssh.exe`），`~/.ssh/config`、密钥、ssh-agent、跳板机配置都能直接用。
- **汇总在客户端**：同时请求每台服务器，合并结果。服务器保持单机版。

### 4.1 添加服务器（以 SSH 为根）

1. 从 `~/.ssh/config` 里选一台主机，或者手填 `user@host`。主机别名就是这台服务器在客户端里的名字（`gpu1`），任务编号显示为 `gpu1-42`。
2. 客户端通过 SSH 检查服务器上有没有 danlu：
   - 没有：进入部署流程（第 6 节）；
   - 有：执行 `danlu info --json`，拿到访问地址、安全入口、CA 指纹和版本。版本和客户端不一致时提示升级。
3. 执行 `danlu token create --name <电脑名>` 领一个设备令牌，存进系统凭据库（Windows 凭据管理器；以后 macOS 上是钥匙串）。令牌长期有效，可以在面板设置页或通过 SSH 随时吊销。
4. 用令牌通过 HTTPS 连一次，确认可用。

整个过程不用输面板密码，也不用复制粘贴：能 SSH 登录就已经证明了身份。证书重新生成后 CA 指纹会变，客户端通过 SSH 重新读取即可。

## 5. 界面

### 5.1 主窗口

```
┌──┬────────────────────────────┬────────────────────────┐
│▣ │ gpu1 ■■■■□□□□  gpu2 ■■□□   │ gpu1-42  vit lr3e-4    │
│☰ │ gpu3 ✕ 连不上              │ ● 运行中 62%  2h10m    │
│⌸ │────────────────────────────│ [取消] [重跑] [快照]   │
│  │ [服务器▾] [项目▾] [状态▾]  │ ── 日志 ────────────── │
│  │ ● gpu1-42  vit     62%     │ epoch 12 |████▌  | 62% │
│  │ ● gpu2-17  vit     40%     │ loss=0.412 lr=3e-4     │
│⚙ │ ✕ gpu3-08  rl      失败    │                        │
└──┴────────────────────────────┴────────────────────────┘
```

| 页面 | 内容 |
|---|---|
| 总览 | 顶部是空卡条，下面是任务列表，详见下文 |
| 历史 | 所有服务器上已结束的任务，按结束时间合并；可以按名称和命令搜索，筛选方式和总览相同，也在右侧分栏看详情 |
| 服务器 | 每台一张卡片：在线状态、版本、体检结果、运维操作（第 6 节）；添加服务器 |
| 设置 | 通知、开机自启、已登录的设备、关于 |

**空卡条**：服务器只有 2–3 台，每台的卡都展开显示：

- 利用率、显存、占用者（自己的哪个任务，或者外部进程）；
- 利用率小曲线，显示最近 5 分钟。数据由客户端轮询时自己积累，服务器不用改；客户端刚启动时曲线是空的；
- 外部进程详情：哪个用户、占了多少显存；
- 连不上的服务器保留最后一次拿到的状态，整体变灰，标出"5 分钟前"（❓ 见第 12 节）。

**任务列表**：

- 范围：所有服务器上运行中、排队的任务，加上 24 小时内结束的任务。
- 排序：不分组，按状态排：没看过的失败 → 运行中 → 排队 → 已结束，同一类里按时间。服务器和项目靠筛选区分。
- 每个任务占一行：状态图标、编号（`gpu1-42`）、项目、名称、卡号、进度或状态、时长。鼠标悬停时显示最新一行日志。

```
● gpu1-42  vit        lr3e-4   0-3  62%  2h10m
● gpu2-17  vit        lr1e-4   0-1  40%  1h05m
◌ gpu1-43  diffusion  base     排队 #1  需 4 卡
✕ gpu3-08  rl         ppo-v2   失败 exit 1  12m 前
```

**任务详情**（右侧分栏）：状态、操作按钮（取消、重跑、复制）、实时日志、代码快照（commit、未提交改动、文件浏览）。日志支持跟随最新输出、`Ctrl+F` 搜索、自动换行开关、下载完整日志；tqdm 进度条原地刷新。

### 5.2 托盘

- 图标分三种状态：一切正常、有任务在跑、有还没看过的失败或异常。第三种显示红点，打开对应的任务后红点消失。
- 单击图标或按全局快捷键（默认 `Ctrl+Alt+D`，可在设置里改），在托盘旁弹出迷你总览：各台的空卡、运行中的任务和进度、未读的失败和异常。
- macOS 上托盘对应菜单栏图标，快捷键对应 `⌘⌥D`。
- 迷你总览**只看不操作**，避免在小窗里误点。点其中任何一项，打开主窗口并定位到它。
- 关闭主窗口时缩回托盘；默认开机自启。

### 5.3 提交、重跑和复制

- 先选服务器，再选这台上的工作目录（最近用过的目录 + 目录浏览）、conda 环境、卡数或指定卡号、命令、环境变量。
- 项目名就是工作目录的最后一级（`~/code/vit` → `vit`）。各台服务器上同一个项目的目录名相同，只是前面的路径不同。
- **命令历史**：按项目列出最近用过的命令，选一条再改。历史直接从各台服务器的任务记录里取，客户端不用另存。
- **复制任务**：任何任务（包括别的服务器上的）都可以复制到提交表单，所有字段预先填好，改完再提交。重跑就是"复制后不改，直接提交"。
- **复制到另一台**：第一次要手动选目标服务器上的目录和环境；客户端会记住"项目 × 服务器 → 目录、环境"，下次自动填好。

客户端只装在一台电脑上，所以已读状态、目录对应关系、界面偏好都只存在客户端本地，不需要同步。

### 5.4 视觉风格

一个和平台无关的现代开发者工具：在 Windows 和以后的 macOS 上看起来一样。做工参照 Linear、Raycast、Arc，但更克制。和面板的视觉互不相干。

**原则**

- 颜色只用来表示状态。界面本身是中性灰，选中项和主按钮也不用彩色；唯一的品牌色是火焰标志的朱砂色。
- 层次靠底色台阶和细边区分；投影只用来托住浮起的面板，不做装饰。
- 编号、数字、命令、路径、日志一律用等宽字体；不为好看降低信息密度。
- 主题跟随系统，深浅两套同样完整。日志终端在两种主题下都是深色。

**颜色**（示意稿里的取值，出正式界面稿时再细调）

| 用途 | 深色 | 浅色 |
|---|---|---|
| 窗口底 | `#0a0b0d` | `#e8eaee` |
| 内容面板 | `#121317` | `#ffffff` |
| 详情卡片、空卡格 | `#18191e` | `#f6f7f9` |
| 选中、悬停 | `#1e2026` | `#eff0f3` |
| 主文字 / 次文字 / 弱文字 | `#eeeef1` / `#a3a5ad` / `#676a73` | `#16171b` / `#5b5e66` / `#8d9098` |
| 细边 | 白色 6% | 黑色 7% |
| 主按钮 | 白底黑字 | 黑底白字 |
| 运行 / 成功 / 失败 / 外部占卡 | `#5aa7ff` / `#4fd18b` / `#ff6b6b` / `#f5b14c` | `#1f6fe0` / `#15803d` / `#dc2626` / `#b45309` |
| 日志终端 | `#0b0c0e` | `#111215` |

排队、已取消用弱文字色。

**字体**

- 正文用 Geist；编号、数字、日志用 Geist Mono。两者都是开源字体，随客户端一起打包。中文用系统黑体：Windows 上是微软雅黑，macOS 上是苹方。
- 字号：正文 12.5px，编号和数字 11–11.5px，详情里的任务名 15px。数字一律等宽对齐。

**形状与层次**

- 四层结构：窗口底 → 内容面板 → 详情卡片 → 日志终端。
- 圆角：窗口、内容面板、详情卡片 10px；托盘浮窗 12px；日志 8px；按钮、筛选项、任务行、空卡格 6px。
- 内容面板：深色模式用一圈白色 6% 的细边加很淡的投影，浅色模式用黑色 6% 的细边加柔和投影。详情卡片只靠底色和细边区分，不加投影。按钮不做高光。
- 窗口材质用纯色，不用云母、亚克力或 macOS 的半透明效果：两个平台效果不同，Tauri 的透明窗口也有已知问题。以后想加，只加在左侧导航栏。

**关键组件**

- **空卡条**：热力色块。每张卡的底色按利用率深浅着运行蓝；被外部进程占用的卡着琥珀色，并加琥珀色描边。格子里是卡号、占用者、最近 5 分钟的小曲线、利用率和显存。服务器名下写"空 N"；离线的服务器整排变淡，写"5m 前"。
- **任务行**：单行，高 30px。选中的行有底色和一圈内描边；行尾红点表示没看过的失败。
- **详情卡片**：编号、任务名、状态和进度条、操作按钮、commit、日志。日志上方有一条工具栏：左边是"实时"呼吸圆点，右边是搜索。
- **标题栏**：自己绘制。左边是火焰标志，中间是 `Ctrl K` 搜索框；Windows 上右边是窗口按钮，macOS 上换成左边的红黄绿圆点。
- **托盘浮窗**：从上到下是未读失败（淡红底条）、各台的热力色块和空卡数、运行中的任务和进度条，底部是"打开主窗口"和快捷键。

**动效**

- 运行中图标匀速转圈；日志的"实时"圆点呼吸。
- 任务状态变化时，整行用新状态的颜色闪一下，约 1.2 秒淡出。
- 切换任务时，右侧详情淡入并上移 4px，150ms。
- 空卡条的颜色和数字 300ms 过渡，小曲线的新数据从右边推入。
- 托盘浮窗从托盘方向淡入，同时从 98% 放大到 100%，160ms。
- 按钮和任务行的悬停底色 120ms 过渡。
- 系统开启"减少动态效果"时，以上全部关闭。

**键盘优先**：常用操作都有快捷键（第 5.5 节），C3 再加 `Ctrl+K` 命令面板。

本节是 C2 之前定下的方向。C2 照它做完界面后，由 impeccable 从实际代码生成了 `desktop/DESIGN.md`，以后以那份为准；弱文字色在那里调到了 4.5:1 的对比度（第 9.2 节）。

## 6. 运维

每个运维动作都是"通过 SSH 执行一条命令"，界面上显示执行了什么命令和它的输出。

| 动作 | 做法 |
|---|---|
| 部署新服务器 | 检查前提（systemd、`nvidia-smi`、CPU 架构）→ 上传客户端自带的程序 → `danlu init --yes …` → `danlu install-service` → 领令牌 → 加入列表 |
| 批量升级 | **先升一台**：上传为 `danlu.new` → `mv` 覆盖 → `systemctl --user restart danlu`，确认服务正常、已经接管正在跑的任务之后，再一键升级其余的。重启不会中断训练 |
| 服务管理 | 重启服务、查看 `journalctl --user -u danlu`、改密码、换安全入口、改端口、重新生成证书 |
| 机器体检 | `danlu doctor --json`：磁盘余量、驱动和 CUDA 版本、conda、linger、服务状态、证书到期时间 |

- **程序从哪来**：客户端安装包自带 linux-amd64 和 linux-arm64 两个 danlu 程序，部署和升级都用它们，所以客户端和服务器的版本始终一致。客户端更新之后会提示"有 N 台服务器版本落后"。开发时可以改用本地 `dist/` 里刚构建的文件。
- **客户端做不了的事**，给出要执行的命令或操作提示：
  - 需要 sudo 的 `loginctl enable-linger`；
  - 改端口后在云安全组里放行新端口。
- **升级第一台后怎么确认没问题**：客户端自动检查两件事：`/api/me` 返回的是新版本；升级前在跑的任务现在都还在跑（说明新进程接管成功）。两项都通过，才能点"升级其余 N 台"。任何一项不通过就停下来，显示 `journalctl` 的最后几十行。
- **服务管理对客户端的影响**：
  - 改密码：只影响面板登录。客户端用的是令牌，不受影响；
  - 换安全入口：客户端不受影响（令牌不经过入口检查）。界面上会显示新地址，方便你更新浏览器书签；
  - 改端口、重新生成证书：客户端通过 SSH 重新读取 `danlu info --json`，自动更新地址和证书指纹。

## 7. 通知

- 只报两类事：
  - 任务失败。通知里写服务器、编号、名称、退出码和最后一行日志；
  - 服务器异常：连不上、卡被外部进程占用、磁盘快满、`nvidia-smi` 报错。
- **外部进程占卡只在影响你时才报**：外部进程出现在你的任务正在用的卡上（可能抢显存导致 OOM），或者挡住了你排队的任务。和别人共用服务器时，平常的占卡不会打扰你，只在空卡条上标出来。
- **同一件事只报一次**：服务器连续 30 秒连不上才报，只报一次，恢复后再报一条"已恢复"；同一个外部进程不重复报。
- 点通知会打开主窗口，定位到对应的任务或服务器。做法：点通知会再启动一次客户端，单实例插件把它转给已经在运行的那个，后者定位到 10 分钟内最近一条通知指向的地方。开发版的通知以 PowerShell 的名义发出，能否弹出取决于系统的专注模式。
- 轮询、判断该不该通知、托盘图标都在 Rust 层：窗口隐藏后网页的定时器会被降频，放在界面里就收不到通知。已读状态和"每台通知到哪个结束时间"也存在 Rust 层（应用数据目录的 `state.json`），所以重启客户端不会重复通知。
- **已读**：在右侧分栏打开过的失败任务算已读，也可以"全部标为已读"。
- 电脑睡眠或关机期间失败的任务，醒来后合成一条通知补报。
- **刷新频率**：主窗口打开时每 3 秒刷新一次；只在托盘时每 10 秒一次，所以通知最多晚 10 秒左右。
- 手机推送（ntfy）以后再说。

## 9. 技术栈与仓库结构

| 层 | 选型 |
|---|---|
| 外壳 | Tauri 2 |
| 界面 | React + TypeScript + Tailwind + TanStack Query（和面板同一套技术，界面代码不共享） |
| Rust 层 | reqwest（rustls，每台服务器单独的根证书）；调用系统的 `ssh` / `scp`；keyring（Windows 凭据管理器，以后 macOS 钥匙串） |
| 字体 | Geist、Geist Mono 随安装包打包 |

```
danlu/
  go.mod  cmd/  internal/   # 服务器
  web/                      # 服务器自带的面板
  desktop/
    src/                    # 客户端界面
    src-tauri/              # Rust 层
  packages/
    core/                   # 两边共享：接口类型、请求函数（发请求的方式由使用方传入）、
                            # 日志处理（tqdm 原地刷新、ANSI）、日志续读和实时流、格式化
  package.json              # 根 workspace，只有 name 和 private
  pnpm-workspace.yaml       # 列出 web、desktop、packages/*；锁文件也在根目录
```

- `packages/core` 只放 TS 函数和不渲染任何东西的 hook，不含组件和样式。
- 服务器和客户端用同一个版本号，一起发布。

### 9.1 发布与自动更新

- **GitHub Actions**：打 tag 时构建 `danlu-linux-amd64`、`danlu-linux-arm64` 和 Windows 安装包（安装包里自带前两个），一起发布到 GitHub Release。
- **客户端更新**：用 Tauri 自带的更新器，启动时和每天检查一次 Release 上的 `latest.json`。有新版本时在托盘提示，确认后下载、安装、重启客户端；重启后接着提示"有 N 台服务器版本落后"。
- **签名**：更新包必须用 Tauri 的更新密钥签名，私钥放在 GitHub Actions 的 secret 里。这和 Windows 代码签名是两回事；安装包没有代码签名，第一次安装时 SmartScreen 会提示，自己用可以接受。
- ❓ 仓库目前还没有远程。客户端必须不登录就能下载到更新文件：仓库公开最简单；如果仓库私有，需要另找一个公开的地方放发布文件，比如单独建一个只放 Release 的公开仓库。

### 9.2 设计上下文（impeccable）

根目录的 `pnpm-workspace.yaml` 列出了 `web` 和 `desktop`，所以 impeccable 处在多应用模式，把两者当作两个应用，分别读取各自的设计文件。即使 `desktop/` 目录还不存在也是这样。

这里只用 pnpm workspace 来声明应用，不在 `.impeccable/config.json` 里另设 `projectRoots`。两种办法效果相同，但只用一种，应用列表就只维护在一个地方。

下面两条规则已经在一个结构相同的模拟仓库里验证过：

- **`PRODUCT.md`、`DESIGN.md`**：从目标目录往上找，用最近的一份。子目录里的文件会整份替换根目录那份，不会合并。
- **界面约定（`.impeccable/surfaces/*.md`）**：只在各应用自己的 `.impeccable/surfaces/` 里找，`primary_target` 写相对该应用目录的路径（如 `src`）。根目录下的界面约定会被忽略。

结构（带"待建"的还没有）：

```
PRODUCT.md                               # 面板的产品定位，web/ 继承这份
web/DESIGN.md                            # 面板的视觉系统
web/.impeccable/design.json              # 面板 DESIGN.md 的 sidecar
web/.impeccable/surfaces/web-src.md      # 面板的方向约定，primary_target: "src"
web/.impeccable/critique/                # 面板的评审记录
desktop/PRODUCT.md                       # 客户端的产品定位，替换根目录那份（C1 写成）
desktop/DESIGN.md                        # 客户端的视觉系统（C2 生成）
desktop/.impeccable/design.json          # 客户端 DESIGN.md 的 sidecar
desktop/.impeccable/surfaces/desktop-src.md  # 客户端的方向约定，primary_target: "src"（主窗口和托盘浮窗共用一份）
```

**不要把界面约定或 `DESIGN.md` 放回仓库根目录**：根目录的界面约定会被忽略；根目录的 `DESIGN.md` 则会被 `desktop/` 继承，impeccable 会把它当成客户端已有的设计去延续。`.gitignore` 里 impeccable 的临时文件规则都以 `**/` 开头，对每个应用的 `.impeccable/` 都生效。

检查命令：`impeccable doctor --json --target web/src` 应该找到 `web/DESIGN.md` 和面板的界面约定；`--target desktop/src` 应该找到 `desktop/PRODUCT.md`、`desktop/DESIGN.md` 和客户端的界面约定。

**使用习惯**：

- 每次调用都写明目录，比如"调整 `web/src` 的任务列表""改 `desktop/src` 的托盘浮窗"。不写目录时，impeccable 按仓库根目录处理。
- `desktop/PRODUCT.md` 已在 C1 用 `/impeccable init` 写成，内容取自本文第 1–3 节。根目录那份写的是"Web 面板、手机和电脑同等重要"，不适合客户端。
- C2 对 `desktop/src` 跑了新设计流程。方向是第 5.4 节里用户已经定下的，按 impeccable 的规则"用户钉死的方向优先于抽签"，没有再抽方向；本机没有图像生成，走的是 code-led。方向约定写在 `desktop/.impeccable/surfaces/desktop-src.md`，做完后从实际代码生成了 `desktop/DESIGN.md`。以后对客户端界面的改动按 `desktop/DESIGN.md` 来。
