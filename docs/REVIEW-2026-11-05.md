## P1 · 定版前修复

### 1. 两个数据目录的同号任务会互相杀进程

**WSL 已复现。** 同一个 Linux 用户下，用两个 `DANLU_HOME` 各起一个 danlu（A、B，端口不同）。A 的任务 #1 运行 `sleep 60`，B 提交任务 #1 `true`。B 的 #1 结束时备注「已清理 5 个残留进程」，A 的 #1 随即被判为「进程被外部终止（没有留下退出码）」。

识别任务进程只看环境变量 `DANLU_JOB_ID=<编号>`，而编号在每个数据目录里都从 1 开始。收尾清理残留进程和取消任务时，按这个变量扫描 `/proc` 发信号，同一用户下其他实例的同号进程也会收到。启动中断后的认领（`Adopt`）可能认到别的实例的进程，GPU 上的进程归属也只看这个编号。

会遇到的情况：

- 开发时 `dev-wsl.sh` 的演示服务和 `e2e.sh` 在同一个 WSL 用户下同时跑，两边的同号任务互相杀，e2e 随机失败；
- 用 `rm -rf ~/.danlu` 重装，或换一个 `DANLU_HOME` 试新版本时，旧安装留下的训练还在跑，新实例的同号任务一结束就把它杀掉；
- 实验室多人共用一个 Linux 账号，各自用 `DANLU_HOME` 起面板。

建议改用每个数据目录唯一的标记。已经注入的 `DANLU_RUN_DIR` 是数据目录下 `run/<id>` 的绝对路径，可以直接当身份：查找进程、`Alive` 的环境核对、`Adopt` 和 GPU 归属都改成匹配 `DANLU_RUN_DIR == r.RunDir(id)`。现在正在跑的任务也带着这个变量，升级后照样认得。回归用例：两个数据目录各跑一个同号任务，其中一个结束或被取消时，另一个不受影响；GPU 进程只归到本实例的任务。 [信号与清理](../internal/runner/runner_linux.go#L49) · [收尾清理](../internal/scheduler/scheduler.go#L512) · [认领](../internal/runner/runner.go#L195) · [GPU 归属](../internal/gpu/gpu.go#L112) · [DANLU_RUN_DIR](../internal/runner/runner.go#L129)

## P2 · 后续修复

### 2. 任务名按字符数限制，输出目录名却按字节超限

**WSL 已复现。** 提交一个 90 个汉字的任务名（没有超过 100 字的限制），任务一启动就失败：「写入任务清单失败: mkdir …/2-训训…: file name too long」。输出目录的最后一段是 `<id>-<任务名>`，Linux 单段文件名最长 255 字节，一个汉字占 3 字节，八十多个汉字就超了。这种失败算作快速失败，队列里还有任务时会顺带暂停队列并推送（代码路径）。改名后才启动的排队任务也会遇到。

另一面也有问题：不填任务名时，默认名是「工作目录名-日期时间」。工作目录名超过 90 个字符时，提交直接被拒，返回「任务名太长」（WSL 已复现，HTTP 400）。

建议输出目录这一段按字节截断到 200 字节左右（截在字符边界上），任务名本身照原样保存；默认名先截短目录名再拼时间。回归用例：90 个汉字的任务名能正常启动，输出目录名不超过 255 字节；工作目录名很长时不填任务名也能提交。 [输出路径](../internal/runner/manifest.go#L54) · [默认任务名](../internal/scheduler/scheduler.go#L202) · [快速失败判断](../internal/scheduler/queue.go#L167)

### 3. 快照重跑写在相对路径下的产物反查不到任务

**WSL 已复现。** 快照重跑的任务在 `run/<id>/code/` 里运行，用相对路径写出 `checkpoints/best.pt`。README 说这些文件算训练产物、清理时保留，可 `danlu trace` 和面板的路径反查都找不到对应的任务。反查只看三条线索：输出目录、`danlu.json` 和任务的工作目录，三条都不覆盖 `run/<id>/code/`。

建议反查时识别 `<数据目录>/run/<id>/code/…`，直接对应到任务 `<id>`，可信度和输出目录同级。回归用例：快照重跑写出的 checkpoint 反查到的是这次重跑，不是源任务。 [路径反查](../internal/trace/trace.go#L50) · [README 保留说明](../README.md#L210)

### 4. 不在 `<conda_base>/envs` 下的 conda 环境记不下包清单

**代码路径确认。** 环境列表里，`<conda_base>/envs` 之外的环境以绝对路径作为名字，比如 conda 装在系统目录、用户环境在 `~/.conda/envs/x`。新建表单提交的也是这个路径，任务照常用 `conda activate <路径>` 跑起来。但记录环境包时执行的是 `conda list -n <路径> --export`，而 conda 的 `-n` 只接受环境名，带 `/` 的值会报 Invalid environment name。所以这些任务的环境记录永远是失败，对比页也比不了包。多人共用、conda 装在系统目录的服务器上，这恰好是常见的布局。

建议环境以 `/` 开头时改用 `conda list -p <路径> --export`。回归用例：路径形式的环境能记下包清单，并参与任务对比。 [记录包清单](../internal/runner/recipe.go#L30) · [环境命名](../internal/api/api.go#L376)
