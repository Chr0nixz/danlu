## P1 · 下次发布前处理

### 1. 严格限卡的 root 助手照抄调用者指定进程的组和资源限制

**读代码；最后一步经 containerd 套接字到 root 是推断。** `danlu_pid` 是 stdin JSON 里的字段。助手只核对这个进程的 real uid 等于 `SUDO_UID`，就把它的 real gid、附加组和 `/proc/<pid>/limits` 原样交给 systemd-run。它没有验证这个进程是 danlu，也没有验证调用者控制得了它，所以"只会收紧"在这里不成立。

机器上只要有一个 uid 相同、组不同的进程就能利用。最常见的是没开 userns-remap 的 Docker 容器（Elasticsearch、Kibana 的官方镜像是 1000:0），管理员用 `sudo -u 用户 -g 组` 起的进程也算。拿到 danlu 用户 shell 的人把 `danlu_pid` 指向它，自己的程序就以 gid 0 和容器的 rlimit 运行；面板会话等于 shell，所以面板被攻破也走得到这一步。

附带两点：`limits` 读失败被忽略，单元改用 systemd 的系统服务默认限制；status 和 limits 按 pid 号分两次读，中间 pid 可能被复用。

建议 gid 用 `SUDO_GID` 或用户库，去掉 `SupplementaryGroups`，让 systemd 按 `User=` 做 initgroups。要保留"照抄 danlu 进程"的话，只接受助手自己祖先链上的 pid。limits 读不到就拒绝。修完把 `Protocol` 加 1：`check` 只比协议号，不加的话旧的 root 副本会继续被当作可用。 [助手](../internal/strict/helper_linux.go#L87) · [ParseStatus](../internal/strict/strict.go#L334) · [systemd-run 参数](../internal/strict/strict.go#L392)

### 2. 严格启动的失败收尾有三个洞

**取消丢失和无限重启是模拟；"回答丢失而单元已经起来"的真实时序是推断。** 都在 `finishStrictStartLocked` 和 `startStrict` 里，普通任务的三步启动不受影响。

- **期间到达的取消被丢掉。** 锁外调助手时用户点取消，`Cancel` 只置 `ls.cancelled` 并返回成功。助手随后失败，失败分支不看这个标记，直接把任务放回队列，`CancelRequested` 被清掉。助手恢复后任务照常启动并占卡。启动越慢，用户越可能在这个窗口里取消。
- **一报错就认定没启动。** 失败后不看 pid 文件、不按标记找进程，助手的出错路径也不停单元。单元其实已起来而回答没传回来时（stdout 混进别的行导致 JSON 解析失败、D-Bus 超时、客户端 40 秒超时关了管道），任务脱管运行，面板显示排队；之后再启动一份，`prepare` 会删掉第一份的 pid 和 exitcode，两份写同一个输出目录。重试写的 env 文件和上一次同名，晚到的旧单元还可能把它读走。
- **成功但拿不到 pid 时无限重启。** 助手返回成功而 MainPID 是 0、pid 文件也没有（`danlu job-exec` 在 exec `run.sh` 之前就失败，比如环境超过 ARG_MAX、日志打不开），任务被记成 `running, pid=0`，下一轮 `reconcile` 判成"从没启动过"放回队列。这条路不计入"只重试一次"，也不触发快速失败，每约 2 秒做一次快照、调一次 sudo、建一个临时单元。

建议：失败分支先判断 `ls.cancelled`，是就转 `cancelled`；sudo 执行过以后的任何失败都按"可能已启动"处理，先 `Adopt` 或按标记 `KillAll` 再放回队列；助手在 systemd-run 出错时对自己起的单元执行 `systemctl stop`；`call()` 只解析 stdout 最后一行；env 文件名带每次启动的随机后缀；启动成功而 `PID == 0` 时直接 `finalize`。 [收尾](../internal/scheduler/scheduler.go#L1038) · [startStrict](../internal/runner/runner_linux.go#L70) · [助手回答解析](../internal/strict/client_linux.go#L50) · [reconcile](../internal/scheduler/scheduler.go#L628)

### 3. 清理会删掉快照重跑任务的产物

**复现（两个场景）。** 11-04 第 1 条的修复不完整：区分"恢复出来的代码"和"产物"只看路径是否在快照清单里，`run/<id>/` 下 `code/` 之外的东西全当丹炉文件。

- 工作目录里上一次运行留下的 `results/metrics.json` 没被忽略且小于 1 MB，进了快照。重跑任务用相对路径把它覆盖成新结果，清理时它是"清单里的普通文件"，被删掉。
- 重跑任务写 `../outputs/best.pt`，文件落在 `run/<id>/outputs/`，清理时整个删掉，还计入 `max_total_gb`。

README 承诺写在相对路径下的文件算训练产物、清理时留下。默认 90 天后静默发生。

建议恢复时记下每个文件的大小和 mtime，清理时只删两者都没变的；`run/<id>/` 下只删丹炉自己写的名字（`run.sh`、`cmd.sh`、`pid`、`exitcode`、`oom_kill`、`env`），其余留下。 [清理运行目录](../internal/retention/retention.go#L225)

### 4. 工作目录里有未登记的嵌套 git 仓库时，"用快照重跑"必然失败

**复现。** `git ls-files --others` 把未跟踪的嵌套仓库列成带尾斜杠的 `third_party/lib/`。`Take` 原样写进跳过清单，快照显示成功；`Restore` 用 `fs.ValidPath` 校验时拒收，报"快照清单包含无效路径"。项目里 `git clone` 过一个依赖、没加进 `.gitignore` 也不是子模块，就会这样。这算启动失败，开着快速失败时还会暂停队列并推送。

文件名不是合法 UTF-8 时是同类问题：`Take` 能写进包，恢复和对比都拒收（推断）。

建议 `gitFiles` 去掉尾斜杠；`Restore` 也要容忍已有清单里的尾斜杠，否则磁盘上现有的快照仍然用不了。 [gitFiles](../internal/snapshot/snapshot.go#L294) · [恢复时的校验](../internal/snapshot/restore.go#L170)

### 5. 后台 `git status` 超时被杀后，在用户仓库里留下 `.git/index.lock`

**复现（macOS，git 2.54；Linux 上机制相同，没有跑）。** `git status` 默认会拿 `index.lock` 回写索引，扫描未跟踪文件期间一直持有。调用时没有设 `GIT_OPTIONAL_LOCKS=0`，超时又是 SIGKILL 整组，git 来不及删锁。大仓库或慢存储上 `git status` 超过快照的 10 秒，或超过重跑表单的 5 秒，或用户中途关掉页面，之后用户自己的 `git add/commit/checkout` 就报 "Another git process seems to be running"，要手动删锁文件。即使不超时，任务启动时刚好撞上用户在提交，用户那边也会失败。

建议两处 `cmd.Env` 都加 `GIT_OPTIONAL_LOCKS=0`，git 文档对后台调用就是这么建议的。 [快照的 git 调用](../internal/snapshot/snapshot.go#L236) · [重跑表单的 gitHead](../internal/api/api.go#L479)

### 6. 推送语言选 English 永远不生效

**读代码，加一个从 `UpdatePrefs` 写入再读回的临时测试。** 面板偏好按 JSON 存库，`ui.notify_lang` 在库里是带引号的 `"en"`。`serve` 里 `notifier.Lang` 用 `GetSetting` 原样返回，`lang()` 拿它和不带引号的 `en` 比较，永远不相等，回退中文。`GET /api/settings` 回显的是 en，所以面板上看不出来。现有测试直接给 `s.Lang` 赋 `"en"`，绕过了这段接线。

建议 `Lang` 改用 `settings.LoadPrefs(st)["notify_lang"]`，补一个从 `UpdatePrefs` 到 `Service.lang()` 的测试。`danlu notify test` 也没设 `Lang`，一并接上。 [serve 的接线](../cmd/danlu/main.go#L341) · [偏好写库](../internal/settings/prefs.go#L225) · [lang()](../internal/notify/messages.go#L187)

### 7. 一次后台刷新失败，整页换成报错框

**读代码，没有在浏览器里运行。** 任务详情、设置、终端、新建任务这四个页面只要 `query.error` 非空就整页渲染 `ErrorBox`，不管手里还有没有上一份数据。重试条件是 `!(err instanceof ApiError && err.status < 500)`，网络错误的 status 是 0，所以断网和服务重启时一次都不重试。资源页已经按"有旧数据就降级显示"处理，这四处没有。

- 设置页（5 秒轮询）：手机上改了几项还没保存，一次轮询失败，分组组件被卸载，改动全丢。
- 运行中任务的详情页（2 秒轮询）：`LogViewer` 被卸载重挂，滚动位置、搜索结果、正在写的备注和改名都丢。
- 终端页：手机从后台回来，设置重取失败，xterm 被销毁，没有自动恢复。
- `danlu restart` 或升级期间，所有开着的详情页都会闪一次。

建议整页报错只在 `!data` 时出现，有旧数据时在页内显示一条提示；重试条件改成只排除 4xx。 [重试条件](../web/src/main.tsx#L28) · [任务详情](../web/src/pages/JobDetail.tsx#L89) · [设置](../web/src/pages/settings/SettingsLayout.tsx#L91) · [终端](../web/src/pages/Terminal.tsx#L82) · [新建任务](../web/src/pages/NewJob.tsx#L99)

### 未提交的 `openStore` 改动

主路径是对的：除 `serve` 外没有别的 `store.Open` 调用；库比程序新时仍然拒绝；库不存在时 `init` 照常在锁内建库；`replace`、`update`、`restart`、`logs`、`ca`、`port`、`cert` 不碰库，升级工具不会被挡住；systemd 启动的服务撞上锁会退出，3 秒后重试。有三点要补：

- **窗口还在。** 旧服务不在的任何瞬间都算"没有服务"：`RestartSec=3` 的重启间隙、`danlu restart` 途中、`systemctl stop` 之后、开机后服务还没起来。hsy 那次事故的同一操作只要落在这个间隙里，库照样被升级。更稳的规则是命令行只建新库，已有的旧库一律拒绝并提示启动或重启服务，锁也就不用抢了。
- **提示语不对。** `replace --no-restart`、手工 `mv`，或 `replace` 换完文件后重启失败，这三种情况下磁盘上已是新程序、服务还是旧进程。此时提示再执行一次 `replace` 会报"新程序和要替换的是同一个文件"，该提示 `danlu restart`。
- **`init --force` 的顺序。** 它先重新生成 CA 再开库。旧服务在运行、用新程序执行时，等 5 秒后报"数据库是旧版本"退出，但 CA 已经换掉，运行中的服务一分钟内加载新证书，所有设备失去信任。 [init](../cmd/danlu/main.go#L245)

## 本轮没有覆盖的部分

- `web/src/locales` 和 `desktop/src/locales` 只核对了键集和占位符，没有逐条读文案；`index.css` 和视觉设计没有看。

- 桌面客户端在 Windows 上的实际行为、对真实服务器的 HTTPS 和全部 SSH 流程。
- 内核或 systemd 挂不上设备 BPF 程序时，严格单元会不会不带过滤照常运行；`check` 目前没有功能性自检。SELinux enforcing 主机上 PID 1 能否执行家目录里的 danlu。
- 资源页的数值口径没有和采样器逐项核对。

## 真机验收缺口

本轮新增，对应上面标"推断"的条目：

- 重启服务器后的第一个严格 GPU 任务能否正常初始化 CUDA（`nvidia-uvm` 按需加载）。
- Ray 或其他调用 setproctitle 的任务：`scripts/s0/gpu-procs.sh` 里它的 worker 还带不带 `DANLU_RUN_DIR`，面板上是不是被标成外部进程。
- 在 events 表里查 `blocked:` 开头的告警有没有抬起后几秒内又清除的记录，确认队首阻塞的误报是否真的发生：`sqlite3 ~/.danlu/danlu.db "SELECT id, ts, kind, key FROM events WHERE key LIKE 'blocked:%' ORDER BY id DESC LIMIT 40"`，看同一个 key 的 `alert_raised` 和 `alert_cleared` 的 `ts` 是否只差几秒。
- 密码进入过期提醒期或 sudo 另有输出时，助手的 stdout 是否多出一行。
- 安卓手机上网页终端的 Ctrl 锁定和自动大写。
- 严格限卡的 e2e 一节在 GitHub runner 上的结果。

完整的定版场景和标准见 [ROADMAP.md](ROADMAP.md#8-做到什么程度算完)，真机检查步骤见 [S0 检查清单](../scripts/s0/CHECKLIST.md)。
