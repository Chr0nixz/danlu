**为什么这样排**

- **S0 持续补验。** 用户已在日常使用，暂未反馈异常。按 2026-11-02 的决定，不等完整清单跑完就继续开发；在实际使用中逐项补证据，真实的报错日志和驱动差异用于修正后续实现。未验证的项目不标为通过。
- **S1 紧跟。** 后面的通知、暂停、对比都建立在"任务状态和失败原因可信"上。完整配方的**记录**部分也放在 S1：这些信息只对之后启动的任务有效，越早开始记，到 S4 能拿来对比的历史就越多。
- **S2 在 S3 前面。** 客户端停着，现在没有任何失败提醒，手机推送是最大的缺口；推送的内容又要用到 S1 的失败原因。
- **S3 不依赖 S2。** 终端、扫码、剩余时间和队列、推送互不相干，有余力时可以和 S2 并行做（分开的 worktree）。
- **S4 只依赖 S1。** 放在后面是因为工作量最大，而且要等 S1 攒下一些带配方的任务。

## 2. 每个阶段都要遵守的约定

- **收尾检查。** 每个阶段结束时跑一遍 AGENTS.md 里的全部检查：`go test`、`GOOS=linux go vet`、`web`、`packages/core`、`desktop` 的 typecheck，`pnpm build`、`cargo test`，以及 `scripts/e2e.sh`。然后部署到真实服务器上实际用起来。
- **接口只做加法。** 新字段和新接口不需要升 `APIVersion`。同一个改动里更新 `packages/core` 的类型和请求函数，并保证 `desktop` 还能编译。如果某个阶段不得不做不兼容的改动，就在那一阶段升版本号，并在本文里注明。
- **数据库迁移只追加。** 每个阶段新增的迁移列在该阶段的"数据库"一栏里，按阶段顺序追加到 `store.migrations` 末尾。
- **Linux 专用代码** 放在 `*_linux.go`，配一个 `*_other.go` 桩，这样在 Windows 上也能编译和跑单元测试。
- **新依赖必须是纯 Go**，以保持静态二进制。计划引入的只有三个：`github.com/creack/pty`、`github.com/coder/websocket`、`rsc.io/qr`。TOTP 自己实现，前端按需引入 `@xterm/xterm` 和 `diff`（jsdiff），都只在用到的页面里懒加载。
- **测试钩子。** 为了在 WSL 里模拟真机情况而加的环境变量（下文的 `DANLU_BOOT_ID_FILE`、`DANLU_MEMORY_EVENTS`），只在设置了的时候才生效。功能做完后写进 AGENTS.md 的 Commands 一节。
- **真实样本。** S0 和 S1 期间在真机上遇到的报错日志，脱敏后放进 `internal/logs/testdata/`，作为失败原因归类的测试样本。
- **边做边用。** 真机清单随日常训练逐项补齐，S0 不阻塞后续开发；每次只补验这次改动涉及的场景。完整清单和未验证的异常路径留作定版前检查。ROADMAP.md 第 8 节要求的两周试用，从 S4 部署到所有服务器后开始计时。
- **状态同步。** 每做完一项，就把 ROADMAP.md 第 4 节对应行的状态改掉。

## 4. S1 · 状态可信

**目标**：不管出了什么意外，任务状态都不撒谎；失败任务一眼就能看出原因；从这一阶段起，每个任务都记下完整的配方。

**顺序**：先做第 4.0 节，失败归类（4.2）建立在它上面；4.1 剩下的几项和 4.3 可以穿插着做。

### 4.0 状态转换和事件表（REVIEW.md 阶段 B 的前半部分）

失败归类、推送、快速失败暂停都要知道"发生了什么"，所以先把改状态的地方收拢到一处，并且每次都记一条事件。设计见 [REVIEW.md](REVIEW.md) 第 7.1 节，这里只写这一阶段做哪些。

**状态（2026-11-02）**：第一部分已完成。任务状态在单一入口转换，状态行和 `job_*` 事件同事务写入；事件带稳定去重键，写库失败时和任务状态一起重试。队列/告警事件及 `wait_reason` 留到 S2。

- **只有一个入口。** 调度器里所有改状态的地方（`finalize`、`failQueued`、`reconcile` 放回队列和直接取消、`launch` 的取消和启动失败分支、`Cancel`）都改为调用 `m.transition(j, to, reason)`。它通过新的 `store.Transition` 在同一个事务里写任务和对应的事件。`save()` 只留给不改状态的字段，比如 pid、`tracker_url`。
- **写库失败。** 和现在一样记进 `pending`，下一轮重试。事件跟着任务一起重试：重试成功时写进去的是同一条事件，不会丢，也不会写两遍。
- **这一阶段的事件**：`job_started`、`job_finished`（成功、失败、取消）、`job_requeued`。数据格式见 REVIEW.md 第 7.1 节的表。`queue_*` 和 `alert_*` 两类在 S2 里和推送一起做。
- **备注和原因分开。** `jobs` 加 `notes` 列，"已清理 N 个残留进程"这类说明写进 `notes`，`fail_reason` 只放失败原因。成功的任务也可能有备注，面板上和原因分开显示。
- **测试**：`manager_test.go` 里每个改状态的用例都检查对应的事件；`JobStore` 的测试包装层也能让 `Transition` 失败，验证重试以后事件只有一条。

### 4.1 异常路径

下表里有几行已经在 [REVIEW.md](REVIEW.md) 阶段 A 里做完，做法和这里原来的计划不一样，"现在"一栏写的是做完以后的样子。

| 情况 | 现在 | 还要做 |
|---|---|---|
| 机器重启 | 占位时记下 `/proc/sys/kernel/random/boot_id`（`jobs.boot_id`）。收尾时没有退出码、boot_id 也变了，记为"服务器重启，任务中断" | `fail_kind = reboot` 和 `DANLU_BOOT_ID_FILE` 测试钩子已有自动化覆盖；真机重启随 S0 使用补验 |
| danlu 在启动任务和写库之间被杀 | 不会再出现"进程在跑、库里还是排队"：先把任务写成 running、pid 为 0（占位），再启动；包装脚本第一行写 pid 文件。重启后 `Recover()` 对 pid 为 0 的任务：进程在就认领，跑完了按退出码收尾，从没启动过就放回队列 | 无 |
| 启动后写库失败（比如磁盘满了） | 不杀进程：任务记进内存里的 `pending`，下一轮用内存里的 pid 继续监控并重试写库，不会再启动一次 | 无 |
| 收尾时写库失败 | 同样记进 `pending`，下一轮重试；单测 `TestPendingSaveRetried` | 无 |
| `nvidia-smi` 卡住或驱动掉了 | 每次调用 8 秒超时，连子进程一起杀掉；超过 20 秒没有一次采集完成、或者查不到卡上的进程时，`/api/gpus` 带 `error` 和 `error_since`，调度器暂停分配 GPU，面板显示错误持续时间 | S2 的推送使用 `error_since` |
| danlu 被 OOM killer 杀掉 | `Restart=on-failure` 会把它拉起来，然后接管任务 | 不用改；真机上演练一次 |
| 升级带数据库迁移 | 有待执行的迁移时，先 `VACUUM INTO ~/.danlu/backup/danlu-<时间>-v<旧版本>.db`，只保留最近 5 份；每次迁移和版本号放在同一个事务里；库比程序新时拒绝启动。`replace` 把旧程序留成 `<路径>.prev` | 无 |

### 4.2 失败原因归类

**状态（2026-11-02）**：第一版代码和自动化用例已完成：失败分类持久化，按任务运行期间的 cgroup OOM 计数、日志和退出码判定；任务所用卡出现外部进程时记录 `ext_seen`；详情页可直接跳到首个 traceback。真实训练日志样本和真机 OOM 结果随 S0 日常使用补齐，未验证场景仍不视为通过。

新增 `fail_kind` 字段，`fail_reason` 保留给人看的文字。几种原因按下面的顺序判断，命中第一个就停：

| `fail_kind` | 显示 | 依据 |
|---|---|---|
| `start` | 启动失败 | 现有的"启动失败:"分支 |
| `reboot` | 服务器重启，任务中断 | 没有退出码，boot_id 变了 |
| `host_oom` | 主机内存不足，被系统杀掉 | 退出码 137 或没有退出码，并且 danlu 服务所在 cgroup 的 `memory.events` 里 `oom_kill` 比任务启动时多了。任务进程都留在 danlu.service 的 cgroup 里（`KillMode=process`），所以读得到。读不到这个文件时，只根据退出码 137 写"可能是内存不足"，推送里也写"可能是"；读得到而计数没变时，137 不算内存不足，往下按日志和信号（SIGKILL）判断 |
| `cuda_oom` | CUDA 显存不足 | 日志结尾匹配 `CUDA out of memory`、`OutOfMemoryError`、`CUBLAS_STATUS_ALLOC_FAILED` |
| `nccl` | NCCL 通信超时或出错 | 匹配 `Watchdog caught collective operation timeout`、`NCCL error`、`ProcessGroupNCCL` 加 timeout |
| `exception` | Python 异常 | 现有的 `logs.ErrorLine` 能找到异常行 |
| `signal` | 被信号终止（SIGSEGV 等） | 退出码大于 128，换算出信号名 |
| `killed` | 进程被外部终止 | 没有退出码，也不是重启 |
| `exit` | 退出码 N | 其他非零退出码 |

- **外部进程标记。** `checkRunning` 每轮看一眼任务所用卡上有没有外部进程，出现过就把 `ext_seen` 置 1，只写一次库。归类为 `cuda_oom` 且 `ext_seen` 为 1 时，原因写成"CUDA 显存不足，运行期间卡上出现过外部进程"。
- **代码位置。** 规则放在 `internal/logs.ClassifyFailure`；`scheduler.finalize` 负责组合。真实测试样本后续放进 `internal/logs/testdata/`，用 S0 收集的日志。
- **跳到报错。** 失败任务的详情接口返回 `traceback_offset`：日志末尾 4 MiB 内第一个 `Traceback (most recent call last):` 的字节偏移。DDP 里各个 rank 都会打 traceback，崩溃时的第一个通常就是根因。只读末尾，是为了让收尾在调度锁里保持毫秒级，也避开训练早期打印过、随后又恢复的 traceback。日志页加一个"跳到报错"按钮，从这个偏移开始读。

### 4.3 完整配方（只做记录）

**状态（2026-11-02）**：环境包异步采集、SHA-256 去重、机器/GPU 信息缓存、`DANLU_OUTPUT_DIR` 和会随任务状态更新的 `danlu.json` 已接入；详情页展示机器信息、输出路径并可查看环境包原文。Windows 单测、Linux 目标 `vet`、Linux runner 测试和 WSL e2e（102 项）均通过。路径反查留到 S4；真机信息仍随日常使用补验。

- **环境包列表。** 任务启动后在后台记录，不拖慢启动，超时 30 秒。
  - 指定了 conda 环境时，执行 `$CONDA_BASE/bin/conda list -n <env> --export`，pip 装的包也包含在里面；
  - 没有指定时，执行任务 PATH 里的 `python3 -m pip freeze`。
  - 输出按 SHA-256 存成 `~/.danlu/envs/<hash>.txt`，相同的环境只存一份。记录失败时把原因写进配方，不影响任务运行。
- **机器信息。** 主机名、各卡型号、驱动版本、CUDA 版本。驱动和 CUDA 版本从 `nvidia-smi` 输出表头读取；GPU 型号和 UUID 复用现有采样结果。`gpu.Monitor` 启动时查一次，之后每小时刷新一次。
- **输出目录。**
  - 新配置项 `runtime.output_root`（默认 `~/danlu-outputs`）。启动时创建 `<output_root>/<项目>/<id>-<名称>/`，通过 `DANLU_OUTPUT_DIR` 注入任务；`DANLU_` 前缀本来就是保留的。
  - 目录里写一份 `danlu.json`，内容有 id、名称、服务器、工作目录、命令、环境变量、conda 环境、GPU、git 信息、快照状态、配方、开始时间；任务结束时补写状态、退出码和失败原因。
  - 训练脚本要自己用 `$DANLU_OUTPUT_DIR` 才有效果，这点写进 README。danlu 永远不删这个目录。

  - 新增 `GET /api/jobs/{id}/env`，返回环境包列表的原文。

### 4.5 验收

**e2e 新增**：

- 一个任务从提交到结束，`events` 表里依次有 `job_started` 和 `job_finished`，不多也不少；
- 任务输出 `torch.OutOfMemoryError: CUDA out of memory` 后以 1 退出，归类为 `cuda_oom`；
- 任务输出 NCCL watchdog 那一行，归类为 `nccl`；
- 任务 `kill -9 $$`，同时把假 `memory.events` 里的 `oom_kill` 加一，归类为 `host_oom`；
- 停掉 danlu，杀掉在跑的任务，改掉假 boot_id 再启动，任务归类为 `reboot`；
- 假 `nvidia-smi` 卡住或查不到进程时，`/api/gpus.error_since` 有值；恢复后错误和起始时间都清除；
- 输出目录里有 `danlu.json`，结束后状态已经补上；
- 新任务配方包含主机名、卡型、驱动和 CUDA 版本，详情页与 `danlu.json` 一致；
- e2e 的假 conda 补一个 `bin/conda`：同一个环境跑两次，环境哈希相同，`envs/` 里只有一份文件。

**真机**：在真实的 GPU 上分别造出 CUDA 显存不足和主机内存不足，确认归类正确；有条件的话重启一次机器。

## 5. S2 · 无人值守

**目标**：人不在电脑前时，磁盘不会被写满，一批任务不会接连白白失败，出事了手机上能收到推送。

### 5.1 队列暂停（磁盘不足和快速失败共用）

**状态（2026-11-02）**：手动暂停/恢复、重启后保留状态、队列事件、审计记录及首页/任务页入口已完成。180 项 WSL e2e 通过；手机/桌面与两主题的按钮操作、错误重试已检查。快速失败自动触发见第 5.2 节，磁盘不足保护见第 5.3 节。

- **状态。** 复用 `settings` 表的 `queue.state` 保存全局状态，不另建 `kv` 表。队列状态包括：`paused`、`kind`（`manual`、`fail_fast`、`disk` 三种）、`reason`、`since`、`job_id`；状态和对应队列事件同事务写入。
- **行为。** `schedule()` 在暂停时直接返回。暂停只是不再启动新任务，已经在跑的不受影响。
- **接口。** `GET /api/queue`、`POST /api/queue/pause`、`POST /api/queue/resume`，暂停和恢复都写审计日志。
- **面板。** 首页和任务页顶部显示一条提示，比如"队列已暂停：#42 启动 20 秒就失败了"，旁边是"继续"按钮。排队分组的标题上加一个手动暂停的按钮。

### 5.2 快速失败暂停

- **完成情况（2026-11-02）。** 自动触发已接入现有队列入口；任务失败、结束事件和自动暂停在同一事务提交，写库失败时先在内存暂停并重试，不能越过保护恢复。单测覆盖取消、阈值边界、启动失败、重启恢复及读写失败；132 项 WSL e2e 通过，包含默认阈值、自动暂停、重启保留、手动恢复和关闭开关。真机触发随日常使用补验。
- **触发条件**：任务失败（不算取消），从启动到结束不到 `runtime.fail_fast`（默认 2 分钟，ROADMAP.md 第 10 节），并且后面还有排队的任务。满足时暂停队列，`kind` 记为 `fail_fast`。
  - 从本次启动占位起计时；加载环境、写入输出清单、启动进程失败也计入。尚未占位就被校验为无效的任务不触发。已占位或运行中的任务继续，已有的手动暂停原因保留。
- **关闭**：`fail_fast = "0s"`。
- **恢复**：只能手动。

### 5.3 磁盘余量

- **完成情况（2026-11-02）。** 采集、分区合并、首页展示、低余量提示、调度保护与 ntfy 告警已接入；180 项 WSL e2e 覆盖暂停、不允许手动绕过和恢复调度，单测覆盖恢复滞回、采集不可信、写库失败及保留其他暂停原因。推送实现见第 5.5 节。
- **采集。** `internal/system` 增加磁盘采集（Linux 上用 `statfs`），看三类目录：数据目录、`output_root`、最近用过的 10 个工作目录。按设备号去重，每分钟采一次。
  - 各目录并行查询，每个最多等 5 秒。网络存储卡住时 `statfs` 可能永远不返回：超时的目录标为采集失败，上一次查询返回前不再重复查询，数据目录照常更新，调度不受影响。
- **展示。** `/api/system` 增加 `disks` 字段：路径、总量、剩余。首页的主机状态里显示各分区的剩余空间。
- **两个阈值** ❓：
  - 剩余少于 `runtime.disk_warn_gb`（默认 20 GiB）时，界面提示；ntfy 开启时推送一次，空间恢复后才会再次触发；
  - 数据目录所在分区剩余少于 `runtime.disk_min_gb`（默认 2 GiB）时，暂停队列，`kind` 记为 `disk`。恢复到阈值的两倍时自动恢复；其他暂停原因不自动解除。采集失败或超过 3 分钟未更新时不启动新任务。两个阈值均支持 0 关闭对应策略。

### 5.4 自动清理

- **完成情况（2026-11-02）。** 保留策略、服务定时清理、CLI 预览、标星和筛选、清理标记及面板说明已接入；180 项 WSL e2e 覆盖清理预览、标星与运行保护、输出保留、410 响应及重启后清除中断的环境包采集状态；Linux 单测覆盖符号链接、输出路径重叠、大小和时间策略、恢复中断与进程锁。
- **清什么**：已结束、没有标星的任务的日志、快照和 `run/<id>/`，以及不再被任何任务引用的 `envs/` 文件。数据库里的任务记录保留，补上 `pruned_at`。**不碰 `output_root`**，那是训练的产出。
- **什么时候清**：`[retention]` 配置两项，结束超过 `keep_days`（默认 90 ❓）的，以及总大小超过 `max_total_gb`（默认 50 ❓）时从最旧的开始清。danlu 启动时清一次，之后每 6 小时一次。
- **标星**：`POST /api/jobs/{id}/star` 接受 `{starred:boolean}`；列表支持 `starred=true`。任务行和详情页有星标按钮，任务页可以只看标星的；清理认领期间修改标星返回 409，调度器保存旧任务副本不会覆盖标星或清理时间。
- **命令**：`danlu prune [--dry-run] [--older-than 72h] [--json]`，先看看会清掉什么。显式 `--older-than` 只按指定时长筛选，不被总量规则扩大；0s 表示所有已结束任务。
- **面板**：已清理任务的列表、日志页和代码页明确说明已清理，保留详情与环境信息入口。日志和快照接口返回 410。
- **边界**：输出目录不计入配额，也不清理；重叠路径整项跳过，符号链接不能把删除引出数据目录。Linux 文件锁和数据库认领标记防止清理重入、标星竞态，并恢复中断的清理。环境清单只在没有运行任务/包采集时检查孤儿，仍被任何任务引用的哈希均保留。服务重启会将中断的环境包采集标为未完成，包括已结束任务，避免永久停在采集中而无法清理。两条保留配置均为 0 时关闭自动清理。

### 5.5 手机推送（ntfy）

**完成情况（2026-11-02）**：代码与自动化已完成。180 项 WSL e2e 覆盖本地 ntfy 记录服务、CLI/面板测试、失败合并与跨重启保留、已发送去重、告警恢复、发送重试及关闭；单测覆盖 GPU 错误满 60 秒、磁盘和外部进程边沿、写库失败及回执未知的恢复。手机 App 实际接收与真机触发随日常使用补验。

事件表和 `job_*` 事件在 S1 第 4.0 节已经做好，`queue_paused`、`queue_resumed` 在本阶段第 5.1 节已接入。本节已补上 `alert_raised`、`alert_cleared`，以及 REVIEW.md 第 7.1 节第 4、5 条：告警只在出现和消失的那一刻写，danlu 启动时从每个 `key` 的最后一条事件恢复出"现在有哪些告警"；队首在等什么通过 `wait_reason` 给面板显示。推送从事件表往后读，游标存在 `settings` 里。

- **配置。** `[notify] ntfy = "https://ntfy.sh/<topic>"`，也支持自建的服务器；需要鉴权时再填 `token`。
  - 推荐用 `danlu notify setup` 配置：生成一个很长的随机 topic，写进配置，再在终端里打印订阅地址和二维码，ntfy App 扫码就能订阅。
  - `danlu notify test` 发一条测试消息。
  - `setup --server` 支持自建服务/路径前缀，`--topic` 使用已有 topic，`--token-stdin` 从标准输入读取令牌。重复 setup 保留原订阅，`--new-topic` 才轮换，`--disable` 关闭；配置修改后重启服务。
- **事件。** 调度器只持久化事件，`internal/notify` 在独立 goroutine 消费和发送，网络请求不会阻塞调度：

| 事件 | 什么时候发 | 去重 |
|---|---|---|
| 任务失败 | 等 30 秒，把这段时间里的失败合成一条 | 推送游标存在 `settings` 表里，重启后不会重发 |
| 队列暂停 | 快速失败或磁盘不足触发暂停时。快速失败的那次失败从合并批次里取出，原因写进这条暂停推送，手机只响一次 | 每次暂停发一条 |
| 磁盘快满 | 剩余空间跌破 `disk_warn_gb` 时 | 回到阈值以上之后才会再发 |
| `nvidia-smi` 出错 | `error_since` 超过 60 秒时，恢复后再发一条"已恢复" | 每次出错只发一次 |
| 外部进程挤到自己的任务 | 自己任务的卡上出现外部进程时 | 同一个任务和进程组合只发一次 |
| 外部进程阻塞队首 | 没有这些外部进程时队首原本能分到卡 | 每次阻塞报一次，重启恢复已有告警 |

- **消息内容。** 标题写"<主机名> · 任务失败"，正文写"#42 vit-lr3e-4：CUDA 显存不足"。不带日志内容、路径和安全入口。
  - 点击链接是 `<地址>/jobs/42`，手机上已经进过入口才打得开；
  - 失败用默认优先级，队列暂停用高优先级；
  - 发送失败重试 3 次，再失败就只写日志。
  - 单个失败链接到任务；多个失败链接到失败任务列表。首次开启或切换 topic 不补发历史。
- **持久化。** `ntfy.cursor` 与 `ntfy.state`（待发批次、发送队列和认领）一起提交。HTTP 与本地数据库无法原子提交；若强制中断导致送达结果未知，重启会记录说明并跳过重发。重试使用相同序列标识供支持此功能的 ntfy 客户端合并；丢失回执时无法保证外部服务恰好处理一次。
- **面板。** 设置页显示推送是否开启、最后一次发送的时间、最后一个错误，并提供"发一条测试"按钮（`POST /api/notify/test`）。

## 6. S3 · 手机顺手

**目标**：在手机上看进度、改参数重跑、临时开个终端处理点事，都很顺手。

### 6.1 剩余时间

- **完成情况（2026-11-03）。** `packages/core` 解析标准 `MM:SS`、`HH:MM:SS` 和超过一天的格式；未知 ETA 不显示。Web 任务列表在桌面与手机行内显示"剩 2:34"，摘要去掉重复 ETA；鼠标悬停说明这是当前 tqdm 进度条的估算。没有 API/数据库改动，桌面客户端继续只显示原有进度。
- **做法。** 在 `packages/core/src/format.ts` 用纯函数从 tqdm 那一行的 `[01:23<02:34, 1.2it/s]` 取出剩余时间；出现 `?` 时不显示。任务行在进度附近显示"剩 2:34"。服务器端不用改。
- **局限。** 显示的是 tqdm 对当前这一条进度条的估计。如果进度条是按 epoch 走的，就是这个 epoch 还剩多久。这一点写在鼠标悬停的提示里。

### 6.2 网页终端

设计要点见 ROADMAP.md 第 7.2 节，这里只写落到代码上的部分。

**完成情况（2026-11-03）**：Linux PTY 会话、WebSocket 输入输出与同源限制、3 个会话上限、断线保留 15 分钟及 256 KiB 输出缓冲、任务目录和 conda 环境启动、配置开关、打开/关闭审计均已实现。面板终端页、手机命令输入和按键行、重连与字号设置已实现。Linux 集成测试、三端类型检查及当前 193 项 WSL e2e 通过；安卓输入法、全屏程序和后台重连的真机验收待补。

- **服务器：新包 `internal/terminal`**
  - **会话管理。** 最多 3 个会话；断开后保留 15 分钟；每个会话用一个 256 KB 的环形缓冲保存最近的输出。
  - **启动 shell。** Linux 上用 `creack/pty` 启动登录 shell，用的是 `/etc/passwd` 里的 shell，找不到就用 bash。
    - 环境：danlu 自己的环境去掉 `DANLU_*`，再加上 `TERM=xterm-256color`；
    - 工作目录：通过进程的 cwd 设置，不拼进命令；
    - conda 环境：环境名只能含字母、数字、`_.-`，也可以是绝对路径（`~/.conda/envs` 这类不在 conda 目录下的环境，`conda env list` 只给路径），路径里有特殊字符时加引号；作为第一条命令输入 `conda activate <env>`，用户在终端里看得见。
  - **重连。** 浏览器记下已收到的输出末尾，重连时带上 `?offset=`，服务器只补发之后的部分，再接上实时输出；首次连接补发整个缓冲。补发的起点和浏览器算的不一致（缓冲已覆盖掉一部分）时，先发 `{"type":"offset","offset":N}`。
  - **一个会话一个连接。** 新连接接替旧连接，旧连接以 4001 关闭：手机切后台或换网络后，旧连接常常已经断了，服务器还没发现。服务器每 20 秒 ping 一次，10 秒没有回应就断开，写一帧超过 10 秒也断开。
  - **退出。** shell 退出后会话随之结束；danlu 重启时 PTY 关闭，shell 收到 SIGHUP 退出，训练不受影响。
- **接口**
  - `GET /api/terminal` 列出会话；
  - `POST /api/terminal` 新建会话，参数 `{job_id?}`，带上就在这个任务的目录和环境里打开；
  - `GET /api/terminal/{id}/ws` 是 WebSocket：二进制帧传输入和输出，文本帧传 JSON 控制消息，比如 `{"type":"resize","cols":80,"rows":24}`；
  - `POST /api/terminal/{id}/close` 关闭会话。
  - WebSocket 用 `coder/websocket`。它默认就拒绝跨域握手，这一点不放宽。
  - 打开和关闭写审计日志，记录目录，不记内容。
- **配置**：`[terminal] enabled = true`（ROADMAP.md 第 10 节）。关掉后这几个接口返回 404，面板也不显示入口。
- **面板**
  - **页面。** 新页面 `/terminal`，xterm.js 加 fit 插件，懒加载，深色。顶部可以在最多 3 个会话之间切换。
  - **底部输入。** 一个输入框，带发送按钮和历史记录；上面一排按键：Esc、Tab、Ctrl、Alt、方向键，以及 `|`、`~`、`/`、`-`。Ctrl 和 Alt 点一下锁定，作用于下一个按键。
  - **字号。** 可以调，记在 localStorage 里。
  - **自动重连。** 断开后按退避间隔重连；在后台待过 5 秒以上回到前台、或网络恢复时，不管旧连接看起来是否还在，都关掉重连。被别的页面接走时显示"已在其他页面打开"，不自动重连；点"在这里继续"或页面重新回到前台时接回。
  - **入口。** 电脑上在顶部导航，手机上在底部导航的"更多"里；任务详情页加"打开终端"。
- **类型**：会话列表的类型放进 `packages/core`；WebSocket 的连接代码只放在 `web/src/lib`，客户端不接终端。

## 7. S4 · 追溯到底

### 7.1 配方展示和反查

  1. 路径在 `output_root` 下面：从目录名解析出任务 id；
  2. 从这个路径往上逐级找 `danlu.json`；
  3. 路径在某个任务的工作目录下，而且这个任务的命令里出现过路径中的某一段：作为"可能是"列出来。

### 7.2 两次任务对比

**状态（2026-11-03）**：接口、任务列表选择和详情入口均已接入。详情入口按工作目录筛选近期任务。快照或包清单不可用时，相应区块显示原因，其余记录仍可对比。

- **接口** `GET /api/compare?a=<id>&b=<id>`，返回这几部分：
  - 命令：按 shell 规则切成词，前端按词显示差异，`--lr 3e-4` 和 `--lr 1e-3` 一眼就能看出来；
  - 环境变量：新增、删除、改变的；
  - conda 环境名、GPU 数量和型号、驱动、CUDA；
  - git：commit、分支、有没有未提交的改动；
  - 代码文件清单：直接读两个快照包，逐个文件算哈希，标出新增、删除、改动的文件。快照有大小上限，所以开销可控；结果按两个任务 id 缓存；
  - 环境包：哪些包新增、删除，哪些换了版本。
- **单个文件的 diff**：前端用现有的 `/snapshot/file` 分别取两个版本，再用 jsdiff 在浏览器里算。
- **面板**
  - **入口。** 任务页可以勾选两个任务点"对比"；详情页有"和…对比"，候选是同一个项目最近的任务。
  - **页面。** 新页面 `/compare?a=&b=`，懒加载。依次是命令、环境变量、代码、环境包、机器；代码部分展开就是逐个文件的 diff。手机上各部分上下排列。

### 8.1 机器体检

- **命令和接口。** `danlu doctor [--json]` 和 `GET /api/doctor` 共用同一套检查。
- **检查项。**
  - `nvidia-smi`：驱动和 CUDA 版本、卡数；
  - conda：安装目录、环境数量；
  - systemd 单元：存在、已运行、`KillMode=process`、`Restart`；
  - linger 是否开启；
  - 数据目录和 `output_root` 的剩余空间；
  - 服务器证书和 CA 的到期时间，证书里的 IP 是否和 `public_ip` 一致；
  - 端口在监听；
  - 时间是否同步（`timedatectl` 可用时检查）；
  - danlu 版本和 `api_version`。
- **输出格式。** JSON 是 `{checks:[{id, level, title, detail, fix}]}`，`level` 取 `ok`、`warn`、`fail` 之一。
- **面板。** 设置页加"体检"，可以重新运行。客户端 C3 直接用这份 JSON。

### 8.2 TOTP

- **开关只走命令行。** 用 `danlu totp enable` 和 `danlu totp disable`，和设备令牌一样，能 SSH 登录就证明了身份；面板上只显示是否已开启。
  - `enable` 在终端里打印 `otpauth://` 二维码和密钥原文，要求输入一次验证码确认之后，才写进 `auth.totp_secret`。
- **登录。** 开启后，登录接口需要 `code`：没带或不对时返回 401 和 `need_totp: true`，登录页这时才显示第二个输入框。验证码错误也计入登录限速。
- **算法。** 按 RFC 6238 实现：SHA-1、30 秒、6 位，允许前后各一个时间窗，同一个时间窗的码不能用第二次。
- **设备令牌不受影响。**

### 8.3 首页速度

- **怎么量。** 用 Chrome 的 Fast 4G 节流量首屏：首页要在 2 秒内看到 GPU 和任务（ROADMAP.md 第 10 节）。
- **可能要做的优化。**
  - 代码高亮、终端、对比页都按路由懒加载；
  - 构建时为静态资源生成 `.gz`，服务端按 `Accept-Encoding` 直接返回；带哈希的资源现在已经是长期缓存；
  - 首页的几个轮询请求，看能不能合并。
- **记录。** 量出来的数字记进 `web/DESIGN.md`，以后改版时对照。
