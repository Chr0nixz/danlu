## 2. 第一批：省心

### 2.1 任务备注

**问题**

- `jobs.notes` 现在只由系统写，比如"已清理 N 个残留进程"（[scheduler.go](../internal/scheduler/scheduler.go#L479)）。详情页却把它显示成"备注："（[JobDetail.tsx](../web/src/pages/JobDetail.tsx#L140)），用户自己没有地方写字。
- 标星只能表示"重要"，说不清为什么重要。
- 场景 4 两个月后写论文时，一句"lr 太大，第 3 个 epoch 发散"比翻代码 diff 快得多。

**怎么用**

- 详情页标题下面一行"写备注…"，点开就地编辑。电脑上回车保存、Esc 取消；手机上输入框占满一行，右侧是保存按钮。
- 提交表单在任务名旁边加一个可选的"备注"，用来写事先的目的，比如"验证 warmup 的作用"。重跑和复制时不带过去，因为备注说的是那一次的结果。
- 任务列表：已结束的任务，第二行优先显示备注的第一行，没有备注才显示最后一行输出。运行中的任务仍然显示进度。
- 搜索：任务搜索框同时搜备注。写成 `#基线` 就能当标签用，不另做标签系统。
- 对比页两边各显示自己的备注；`danlu trace` 的输出也带上备注。

**规则**

- 最多 500 字，允许换行，列表里只显示第一行。
- 任何状态的任务都能改，包括日志和快照已被清理的任务。
- 系统写的 `notes` 改为显示成"运行说明"，和备注分开。

**改动**

- **数据库**：`jobs` 加 `memo TEXT NOT NULL DEFAULT ''`。
- **写入**：和标星一样，单独执行 `UPDATE jobs SET memo=? WHERE id=?`（参照 [retention.go](../internal/store/retention.go#L10) 的 `SetStarred`）。不能把 `memo` 加进 `SaveJob` 的列清单：调度器每轮从库里读出任务，再整行写回（[store.go](../internal/store/store.go#L465)）。加进去以后，调度器手里的旧对象会在并发时把刚写的备注覆盖掉。
- **搜索**：`ListJobs` 的关键词条件加上 `memo LIKE ?`（[store.go](../internal/store/store.go#L543)）。
- **接口**：`POST /api/jobs/{id}/memo`，body 为 `{memo}`，返回更新后的任务。`SubmitReq` 加 `memo`。
- **`danlu.json` 不写备注**：备注随时会改，训练产物里的清单以写入时为准，备注以数据库为准。
- **core 和客户端**：`Job.memo?: string`，加 `api.setMemo`；客户端只需保持编译通过。

**验收**：store 单测验证调度器保存任务不会覆盖备注；e2e 验证写备注、搜索命中、重启后仍在；390px 宽度下编辑一次。

### 2.2 结束提醒与跑完汇总

**问题**

ntfy 现在只推失败（[notify.go](../internal/notify/notify.go#L294) 跳过非 `failed` 的结束事件）。"出事才响"是对的，但有两种情况，手机上等不到该有的消息：

- 评测或短任务跑完了，想马上看结果；
- 晚上排的一批跑完了。场景 1 早上看手机时，要打开面板才知道是不是全跑完了；场景 3 里一批提前跑完，卡就一直空着，直到有人发现。

**怎么用**

- 提交表单加一个"结束时推送"勾选框，默认不勾，记住上次的选择（存在浏览器本地）。排队中和运行中的任务，详情页可以随时打开或关掉（铃铛图标）。
- 勾了的任务成功或被取消时推一条，例如"任务完成 · #42 vit-lr3e-4 · 用时 5 小时 12 分"。失败不管勾没勾都推，和现在一样。
- **跑完汇总**。队列从有任务变为空时发送成功、失败和取消的计数与合计任务用时。链接用结束事件 ID 筛出原批次。

**规则**

- **同一件事只响一次。**
  - 成功和失败落在同一个 30 秒合并窗口里时，合成一条，标题改为"任务结束"。
  - 跑完汇总替代同批仍在合并窗口内的待发结束提醒，之前已发出的提醒保留。
  - 快速失败暂停时，仍然只发暂停那一条。
- **一批的范围**。从启用汇总或上一次排空起算。单任务排空也结批，多任务批次才发汇总。快速失败仍计入继续队列后的批次。
- **暂停不算跑完。** 队列因暂停而没有任务在跑时不发汇总，暂停本身已经推过一次。
- 推送内容沿用现有规则：只有编号、任务名和原因，链接不带安全入口。

**改动**

- **数据库**：`jobs` 加 `notify_done INTEGER NOT NULL DEFAULT 0`，单独 UPDATE，理由同 2.1。
- **事件**
  - `job_finished` 的数据加 `notify_done`，转换时从任务上读，写进同一个事务（[transition.go](../internal/scheduler/transition.go#L72) 的 `jobEvent`）。
  - 新增 `queue_drained`：调度器在让"运行中 + 排队 + 启动中"归零的那次转换（收尾或取消排队）里一并写入。它只是一个标记，计数由通知服务在消费事件时累计；计数随通知游标一起持久化，重启不丢。
- **配置**：`[notify] queue_drained = true` ❓。按约定服务不写配置，改了要重启；这只是一个开关，可以接受。
- **接口**：`POST /api/jobs/{id}/notify`，body 为 `{on}`；`SubmitReq` 加 `notify_done`。
- **面板**：表单勾选框、详情页铃铛；设置页的推送区写明会推哪些事件。
- **客户端**：客户端恢复后用自己的系统通知，`notify_done` 只影响 ntfy。

**验收**：notify 单测覆盖成功和失败同窗口合并、汇总与最后一条结束提醒去重、快速失败暂停时不发汇总、重启后计数不丢；e2e 用现有的本地 ntfy 接收服务实际收一次。

### 2.3 日志静默提醒（疑似卡死）

**问题**

- 失败归类只在进程退出后才起作用。进程不退出、也不再前进时，任务一直显示"运行中"，还按严格先来先跑挡住后面整个队列（[scheduler.go](../internal/scheduler/scheduler.go#L510)）。这违背场景 5 的"任务状态不撒谎"，代价是一整夜的卡时。
- 常见原因：DataLoader worker 死锁；等文件锁（例如 HuggingFace 缓存锁）；网络存储卡住，进程停在 D 状态；评测阶段死循环。
- NCCL 挂住时，PyTorch 的 watchdog 通常会在超时（默认约 10 分钟）后中止进程，变成已有的"NCCL 超时"失败，不在这项要解决的范围里。

**判断依据**

- **主信号：日志文件的修改时间。** 正常训练的日志隔几秒就会变，tqdm 写进文件时也会持续刷新。用修改时间就不需要额外持久化，danlu 重启后直接读。
- **阈值随任务自适应**：`max(静默下限, 3 × 这个任务到目前为止最长的一次输出间隔)`，静默下限默认 30 分钟 ❓。每隔很多步才打一行日志的任务，或者评测阶段本来就要安静很久的任务，阈值会自动放宽。最长间隔只记在内存里，重启后从下限重新开始。
- **GPU 利用率不作为判定条件。** NCCL 或 CUDA 同步卡住时卡常常是 100%，DataLoader 死锁时是 0%，两种都是卡死。利用率只写进提醒，帮助判断：
  - 0%："分到的卡空转"；
  - 接近 100%："可能卡在通信或同步"。
- **CPU 时间也不作为判定条件**。按 `DANLU_RUN_DIR` 采集任务进程的 D 状态数量，有数据时附在提醒中。

**怎么用**

- 推送一条，例如"#42 vit-lr3e-4 已 45 分钟没有新输出，分到的卡利用率 0%"，点开是任务详情。
- 任务行在状态旁加一个警告色的"无输出 45 分钟"。运行中的状态颜色不变，只多一个标记。
- 详情页顶部一条提示，带"看日志末尾""打开终端""取消任务"三个操作。
- 日志重新增长时标记自动消失，不推"已恢复"，免得半夜响两次。
- 不自动取消。要自动处理，用 5.3 的"时长上限"，由用户对单个任务打开。

**改动**

- **告警**：`alerts.go` 新增 `silent:<job_id>`，走现有的告警边沿和事件机制（[alerts.go](../internal/scheduler/alerts.go#L36)）。出现时推送，消失时不推。`AlertData` 加 `Since`、`Util`、`DState`。
- **采集**：每 10 秒对每个运行中任务的日志做一次 stat，只 stat 不读内容。日志在数据目录里，stat 很快；但按 P1 第 4 条的教训，仍然放在调度锁外面做，结果缓存给告警用。
- **接口**：任务对象加 `silent_since`。和 `wait_reason` 一样由 Manager 的内存缓存提供，不取调度锁（参照 [alerts.go](../internal/scheduler/alerts.go#L16) 的 `WaitReasons`）。
- **配置**：`[runtime] silence_alert = "30m"`，设为 `0s` 关闭。
- **面板**：任务行标记、详情页提示，首页"运行中"分组标题旁显示静默的任务数。

**不做**：按日志内容判断（NaN、loss 不降）。各家代码打印格式不一样，误报多，W&B 上看更准（第 6 节）。

**验收**

- manager_test：日志修改时间超过阈值后只告警一次；日志恢复增长后清除，且不推送；较长的历史间隔会放宽阈值；重启后从下限重新开始。
- e2e：提交一个先输出几行、然后 `sleep` 的假任务，把阈值设成 20 秒。
- 真机：在 `scripts/s0/jobs/` 加一个故意让 DataLoader 死锁的脚本。

### 2.4 日志搜索

**问题**

- 日志页只加载末尾，往前要一段段加载，完整日志得下载（[LogViewer.tsx](../web/src/components/LogViewer.tsx#L89)）。
- 想看"第 37 个 epoch 的 val acc"或者"第一个 warning 出现在哪"，手机上基本做不到。
- 面板已经能按字节偏移打开日志，"跳到报错"就是这么做的（详情页的 `?offset=`），只差一个找偏移的入口。

**怎么用**

- 日志工具栏加一个搜索按钮。输入关键词后列出匹配行，最多 200 条，关键词高亮。点一条，日志就从那个位置打开。
- 结果之间可以"上一个 / 下一个"跳转。手机上结果从底部弹出，占半屏。
- 一排固定的快捷词：`error`、`warning`、`nan`、`Traceback`、`val`。

**规则**

- 按普通文字匹配，不分大小写；第一版不支持正则。
- 对 tqdm 用 `\r` 原地刷新的行，只看每行最后一段，也就是终端上最终显示的那段。否则搜"loss"会命中上千条中间进度。
- 一次最多扫 1 GiB 或 5 秒，超出就返回已经找到的，并注明"只搜了前 xx%"。运行中的任务以请求时的文件大小为界。
- 已按保留策略清理日志的任务不能搜，和查看日志一致。

**改动**

- **接口**：`GET /api/jobs/{id}/log/search?q=&limit=200`，返回 `{matches: [{offset, text}], scanned, size, truncated}`。分块流式读取，不把整份日志读进内存。
- **后端**：`internal/logs` 加 `Search`。残缺 UTF-8 的处理和 P2 第 8 条修好后的读取逻辑一致。
- **面板和 core**：`LogViewer` 加搜索框和结果面板；core 加 `api.searchLog`。
- **客户端**：现在不接，以后可以直接用同一个接口。

**验收**：logs 单测覆盖 `\r` 折叠、跨块边界的匹配、残缺 UTF-8、扫描上限；e2e 验证用搜到的偏移打开 SSE，能从那里读到内容。

## 3. 第二批：批量

### 3.1 修改排队中的任务与批量操作

**问题**

这是场景 3 的后半截：

- 10 个扫学习率的任务，第一个因为参数拼错 20 秒就挂了。快速失败暂停保住了后面 9 个，但它们带着同一个拼错的参数。
- 现在只能逐个取消，再逐个提交，在手机上要点几十下。
- 排队中的任务还没做快照、也没分卡，改它们没有任何追溯上的代价。

**怎么用**

- 排队中的任务，详情页加"修改"。它打开和"重跑"同一个表单（`/new?edit=<id>`），保存后原地更新，编号和排队位置都不变。
- 任务列表的选择模式扩展一下。现在只能选两个任务做对比（[Jobs.tsx](../web/src/pages/Jobs.tsx#L46)），改成：
  - 选中的都是排队任务时，出现"取消所选"和"替换命令中的文字"；
  - 选两个已结束的任务时，仍然是"对比"。
- 替换：填"查找"和"替换为"，先逐个预览改前改后的命令（按行 diff），确认后一次改完。
- 队列因快速失败暂停时，首页的暂停提示里加一个"修改排队中的任务"，直接进入替换，并选中全部排队任务。改完再点"继续"。

**规则**

- 只能改 `queued` 的任务。能改的就是提交表单上的那些字段；`rerun_of` 和 `code_from` 保持不变。
- 批量替换要么全部改成，要么一个也不改。中途有任务已经开始运行，就整批放弃，并说明是哪个任务已经开始。
- 改过的任务在详情页标出"排队期间修改过"，事件里保留改前的字段。实际跑的是什么，仍以任务上的命令和快照为准。

**改动**

- **后端**：`Manager.Edit(id, req)` 和 `Manager.EditBatch(...)`。两者都持调度锁，复用 `Submit` 的校验（先把校验拆成 `validate(req)`），执行 `UPDATE jobs SET … WHERE id=? AND status='queued'`。
  - **为什么必须进锁**：`schedule` 在锁里读出排队任务并占位，后面 `launch` 用的是读出来的那份命令。编辑也进锁，结果就只有两种：在调度读取之前改完，新命令生效；或者任务已经占位，`UPDATE` 影响 0 行，接口返回 409"任务已经开始"。
  - 任务还在 `pending` 里（写库失败、等待重试）时也拒绝修改。
- **事件**：新增 `job_edited`，数据是改前的字段，和修改在同一个事务里写入。
- **接口**
  - `POST /api/jobs/{id}/edit`，body 和提交相同。
  - `POST /api/jobs/batch`，body 为 `{ids, action, find, replace}`，`action` 取 `cancel` 或 `replace`；带 `dry_run: true` 时只返回预览，不落库。
- **面板**：NewJob 的编辑模式、任务列表的选择模式、暂停提示里的入口。
- **客户端**：只需保持编译通过。

**验收**

- manager_test：编辑和占位竞争，两种先后顺序都覆盖；批量中途有任务开始时整批不改；`pending` 中的任务拒绝编辑。
- e2e：快速失败暂停 → 批量替换 → 继续 → 后续任务用新命令启动。

### 3.2 队列顺序与暂缓

**问题**

- 严格先来先跑本身是对的，大任务不会被小任务饿死。但现在顺序完全由提交时间决定：排队任务按 id 排（[store.go](../internal/store/store.go#L489)）。
- 想让一个急着要结果的评测先跑，只能把前面的任务全部取消再重提。
- 想让某个任务"先别跑，等我确认数据准备好"，没有办法。

**怎么用**

- 排队任务的菜单里有置顶、上移、下移、移到末尾。电脑上的拖动排序放到第二步再做；手机上就用这四个按钮。
- **暂缓**：排队任务可以"暂缓"。暂缓的任务留在队列里原来的位置，显示为灰色，调度时跳过，也不挡后面的任务。"恢复"后按原来的位置参与调度。

**规则**

- 调度仍然严格按顺序：队首（第一个没有暂缓的任务）放不下，后面的都不启动。改变的只是"谁是队首"。
- danlu 停止时放回队列的任务（`job_requeued`）回到原来的位置，不排到末尾。现在这一点靠 id 顺序自然成立，换成排序列以后要保持住。
- 暂缓和快速失败暂停、磁盘保护这些整队暂停互不影响。

**改动**

- **数据库**：`jobs` 加 `queue_order INTEGER` 和 `held INTEGER NOT NULL DEFAULT 0`。迁移时把 `queue_order` 设为 id，新任务插入时也等于 id。
- **存储**：排队任务改按 `queue_order, id` 排，`queue_pos` 用同一个顺序算（[api.go](../internal/api/api.go#L467)）。面板和客户端都按服务器给的 `queue_pos` 排（[Home.tsx](../web/src/pages/Home.tsx#L109)、[fleet.ts](../desktop/src/lib/fleet.ts#L60)），这两处不用改。
- **调度**
  - `schedule` 遇到暂缓的任务时跳过（`continue`）。
  - `alerts.go` 计算队首的等待原因时，跳过暂缓的任务。现在直接取的是 `queued[0]`（[alerts.go](../internal/scheduler/alerts.go#L135)）。
- **接口**
  - `POST /api/jobs/{id}/move`，body 为 `{to}`，`to` 取 `top`、`up`、`down` 或 `bottom`。
  - `POST /api/jobs/{id}/hold`，body 为 `{held}`。
  - 3.1 的批量操作再加 `hold`、`release` 和 `top`。
- **事件**：`job_moved`、`job_held`，只做记录，不推送。

**不做**：优先级数字、"允许插队"（backfill）。单用户手动排序已经够用，插队会让"这个任务为什么还没跑"变得难解释。

**验收**（manager_test）：置顶的任务先启动；暂缓的队首不挡后面的任务；放回队列后位置不变；暂缓的任务不触发"队首等待外部进程"告警。

### 3.3 命令参数编辑

**问题**

- 场景 2 要求"在手机上 30 秒内把 batch size 改小重跑"。
- 现在重跑表单里的命令只是一个文本框（[NewJob.tsx](../web/src/pages/NewJob.tsx#L204)）。一条带十几个参数的 torchrun 命令，在手机上要来回拖光标，安卓输入法还会自动补全、自动改大小写。

**怎么用**

- 命令框下面自动列出识别到的参数，例如 `--batch_size 64`、`--lr=3e-4`、`-c configs/vit.yaml`，每个一行：左边是参数名，右边是输入框。改右边的值，上面的命令跟着变；直接改命令框，下面会重新识别。
- 数值参数旁边有"×2""÷2"两个小按钮。手机上数值框弹数字键盘（`inputmode="decimal"`）。
- 失败原因是 CUDA 显存不足、又识别到像 batch size 的参数（`batch_size`、`bs`、`per_device_train_batch_size` 等）时，失败提示里多一个"batch size 减半后重跑"。它打开预填好的重跑表单，用户确认后再提交。
- 重跑时，如果原任务有资源画像（4.2），参数区上方显示一行"上次显存峰值 41%"，帮助判断能不能加大 batch。

**规则**

- 只改值所在的那一段文字，命令的其他部分（换行、续行符、注释、`&&` 后面的部分）一个字节都不动。
- 识别不了的命令（here-doc，或参数里套着 `$(...)` 之类）不显示参数区，只用文本框。
- 只识别 `--key value`、`--key=value`、`-k value` 三种写法；`--flag` 这类不带值的开关显示成只读标签。
- 值里有空格或特殊字符时，保留原来的引号风格；新输入的值需要时自动加单引号。

**改动**

- **`packages/core`**：加一个带位置信息的 shell 分词器，以及 `parseArgs(cmd)` 和 `setArg(cmd, span, value)`，配单元测试（续行、引号、`=` 写法、多条命令）。放在 core，是因为客户端的提交表单以后也要用。
- **面板**：NewJob 的参数区，FailBox 的"减半重跑"入口。
- **后端**：不改。

**验收**：core 单测覆盖常见的 torchrun、accelerate、`python -m` 命令和几种奇怪写法；390px 宽度下，从失败详情到提交改好的重跑能在 30 秒内完成。

### 3.4 参数扫描与任务组

**问题**

- 场景 3 本身就是"晚上排 10 个任务扫学习率"，现在要提交 10 次。
- 提交以后，这 10 个任务和别的任务混在列表里，看结果要自己记编号。
- W&B 上也不会自动分组。

**怎么用**

- **提交**
  - 提交表单加一个"扫描"开关。打开后，在 3.3 的参数行上点"扫描"，这个参数就变成变量，再填几个值（`1e-3, 3e-4, 1e-4`）。也可以直接在命令里写 `{{lr}}`，在下面的变量表里填值。
  - 多个变量默认取所有组合，可以切换成"按位置一一对应"。
  - 提交前预览会生成哪些任务，以及各自的命令和名字（默认名字形如 `<任务名>-lr1e-3-bs32`），一次最多 64 个。
- **排队**：提交后这批任务挨着排进队列，组成一个"任务组"。快速失败暂停照常生效。
- **列表**
  - 任务列表里一组折叠成一行，例如"扫描 #3 · lr × bs · 12 个：8 成功、2 失败、1 运行、1 排队"，点开展开成员。
  - 首页排队区同样折叠，12 个排队任务不会把首页撑长。
- **组详情页**：一张表，每个变量占一列，后面是状态、耗时、W&B 链接、备注和资源画像（4.2）。
  - 可以按任意列排序，勾两个直接对比。
  - 操作有"取消剩下排队的""重跑失败的""以这组为模板再扫一次"。

**规则**

- 变量只在提交时展开，每个任务记下的都是展开后的完整命令。之后的追溯、对比、重跑和快照，都和普通任务完全一样；组只是一层归类。
- 变量也可以用在环境变量的值和任务名里。
- `{{` 和 `}}` 在 bash 里没有特殊含义，不会和 `${lr}` 这类 shell 变量冲突。值原样替换，不自动加引号：这是用户自己的命令，没有权限问题；值里有空格时，预览会提示。
- 每个成员任务注入 `DANLU_GROUP_ID`。用户没有自己设 `WANDB_RUN_GROUP` 时，再注入 `WANDB_RUN_GROUP=danlu-g<组号>`，W&B 上这批 run 自动归成一组。

**改动**

- **数据库**：新表 `job_groups(id, name, template_json, created_at)`；`jobs` 加 `group_id INTEGER` 和 `params_json TEXT`（这个任务的变量取值）。
- **接口**
  - `POST /api/groups`：body 是提交字段加 `vars` 和 `mode`；带 `dry_run` 时只返回预览。整批在一个事务里插入，要么全部进队列，要么一个也不进。
  - `GET /api/groups/{id}`。
  - `GET /api/jobs` 加 `group` 筛选，列表项带 `group_id`。
  - 展开逻辑只在 Go 里实现一份，预览也走服务器，避免两端算出不一样的结果。
- **环境变量**：`runner` 的注入加上这两项。`WANDB_RUN_GROUP` 只在用户没设时注入，所以不能放进 `ReservedEnv`，放进去就禁止用户自定义了。
- **面板**：表单的扫描模式、列表折叠、组详情页。
- **客户端**：保持编译通过；历史页暂时不折叠。

**验收**

- 展开逻辑单测：取组合与一一对应、数量上限、引用了未定义的变量时报错、名字去重。
- manager_test：一批任务原子插入。
- e2e：提交一个 2×3 的扫描 → 6 个任务按顺序排队 → 第一个快速失败 → 队列暂停 → 用 3.1 批量替换 → 继续。

**依赖**：3.3（参数行上的"扫描"按钮）；3.1 的批量取消可以直接复用。

## 4. 第三批：看结果

### 4.1 输出文件浏览

**问题**

- 训练产出的样例图、评测 JSON、CSV 结果和生成的文本，现在都要开终端 `ls`、`cat`；图片在手机上根本看不了。
- ROADMAP 第 7.2 节说过："哪件事总要开终端去做，就说明面板少了那个功能"。看结果文件大概是最常见的一件。

**两个根目录**

- **输出目录**：`DANLU_OUTPUT_DIR`（[manifest.go](../internal/runner/manifest.go#L53)）。脚本用了这个变量的任务，这里放的就是它独有的产物。
- **运行目录**：工作目录；用快照重跑的任务是 `run/<id>/code/`。很多脚本把结果写在相对路径（`outputs/`、`checkpoints/`）下，而工作目录是多个任务共用的。所以默认只显示"这个任务运行期间改过的文件"，即修改时间落在开始到结束后 1 分钟之间的文件，也可以切换成显示全部 ❓。

**怎么用**

- 任务详情加一个"文件"标签页：面包屑加文件列表（名字、大小、修改时间），默认按修改时间倒序，最新的产物排在最上面。
- **预览**
  - 图片（png、jpg、webp、gif、svg）直接显示。一个目录里的图片可以切成网格浏览，也可以左右滑动。
  - 文本、日志、yaml、py 显示前 2 MiB，JSON 格式化显示。
  - CSV/TSV 显示成表格：前 500 行，表头固定。
  - 其他类型和大文件只提供下载。
- 手机上预览全屏，返回键回到列表。

**规则**

- **只读。** 不提供删除、重命名和上传；删文件不可撤销，交给终端。
- **不出根目录。** 所有访问都限制在根目录以内，符号链接也逃不出去：用 Go 的 `os.Root` 打开（Go 1.24 起提供，项目用的是 1.26）。权限上这不算新能力，终端和提交任务本来就能读任何文件；限制范围是为了界面清楚，也防止误点。
- **不执行内容。** 返回文件内容时加 `Content-Security-Policy: sandbox` 和 `X-Content-Type-Options: nosniff`，SVG、HTML 被直接打开也不会在面板的源下执行脚本。内容类型按扩展名决定，不嗅探。
- **不被存储拖住。** 网络存储可能卡住，所以读目录和递归扫描"改过的文件"都有超时（5 秒）和数量上限（扫描 1 万个条目），也不取调度锁。
- **已清理的任务**：输出目录不在清理范围内，照常能看；`run/<id>/code/` 会被清理，以 P1 第 1 条修好之后的规则为准。

**改动**

- **接口**
  - `GET /api/jobs/{id}/files?root=output|run&path=&changed=1`：列目录。
  - `GET /api/jobs/{id}/files/raw?root=&path=`：取内容。带 `download=1` 时作为附件下载，并清掉写超时（同日志下载用的 `noWriteTimeout`，[api.go](../internal/api/api.go#L173)）。
- **后端**：新文件 `internal/api/files.go`。
- **面板**：JobDetail 的新标签页和预览组件。CSV 用一个简单的解析器，不引入新依赖。
- **客户端**：不接。

**不做**：服务器端生成缩略图（第一版靠浏览器懒加载，手机流量成了问题再加）、在线编辑。

**验收**：单测覆盖 `..` 和符号链接逃逸、超时、"改过的文件"过滤、CSP 头；e2e 让假任务写出图片和 CSV，检查列表和预览；390px 宽度下浏览一个图片目录。

### 4.2 资源画像

**问题**

- 选卡数和 batch size 全凭经验。"这个任务 4 张卡跑满了吗""显存还剩多少，batch 能不能翻倍"，现在只能在任务运行时盯着首页的 GPU 卡片看，结束后什么也没留下。
- ROADMAP 第 5 节已经定了口径：只记汇总数字，不做曲线。

**记什么**（每个任务一份）

- **GPU**：分到的卡的平均利用率，以及每张卡的显存峰值（只算这个任务自己的进程）。数据就在现有的 2 秒采样里：卡的 `util`，以及每个进程的 `used_mem_mb` 和所属任务（`gpu.Proc.JobID`）。
- **主机**。任务进程的内存峰值（RSS 之和），每 30 秒按 `DANLU_RUN_DIR` 采集一次。
- **采样覆盖**：采样次数和覆盖时长，说明这些数字有多可信（danlu 重启期间没有采样）。

**怎么用**

- 详情页"详情"里加一行"资源"，例如：`GPU 利用率 平均 87%（4 卡）· 显存峰值 71.2 / 80 GiB（GPU 2）· 主机内存峰值 48 GiB`。运行中的任务显示截至当前的值。
- 运行 10 分钟以上、平均利用率低于 40% 的任务，详情页给一条灰色提示："GPU 利用率偏低，可能卡在数据加载或 CPU 预处理"。不推送。
- 对比页和组详情页（3.4）各加一栏；重跑表单里的用法见 3.3。

**改动**

- **采集**：Manager 给每个运行中的任务维护一个累加器（利用率之和、采样次数、各卡显存峰值），按采样时间去重（调度循环 1 秒一轮，GPU 采样 2 秒一次）。每 5 分钟和收尾时写库；重启后从库里读回，继续累加。
- **数据库**：`jobs` 加 `profile_json TEXT`，并加进 `SaveJob` 的列清单。这一列只由调度器写，不存在 2.1 那种覆盖问题。
- **接口**：任务对象加 `profile`。
- **面板**：详情页和对比页。

**验收**（manager_test）：用假 GPU 源喂一串利用率，平均值正确；外部进程的显存不计入；重启后继续累加。e2e：在假 GPU 下跑完一个任务后，`profile` 有值。

## 5. 第四批：看需要

### 5.1 命令行提交

**问题**

- 日常流程是：本地改代码 → rsync → 切到浏览器 → 选目录、粘命令、提交。前两步在终端里一条脚本就完成了，最后一步却要换工具。
- 扫描和批量评测有时用脚本生成更方便；让 AI 编程助手改完代码直接跑实验，也需要一个不用浏览器的入口。

**怎么用**

```bash
rsync -a ./ gpu1:~/proj/ && ssh gpu1 'cd ~/proj && danlu submit -g 4 -e torch2 --notify -- torchrun --nproc_per_node 4 train.py --lr 3e-4'
```

- `danlu submit`：工作目录默认是当前目录，打印任务编号和面板里的路径 `/jobs/<id>`（不带安全入口）。
- 另有 `danlu jobs`（列表）、`danlu show <id>`、`danlu tail [-f] <id>`（任务日志）和 `danlu cancel <id>`。`danlu logs` 已经用来看服务日志，所以任务日志用 `tail`。
- 都支持 `--json`，方便脚本和 AI 助手解析。

**规则**

- 能 SSH 登录就证明了身份，和 `danlu token create` 是同一个道理，所以不需要密码或令牌。
- 只连本机正在运行的 danlu，不直接写数据库：所有状态变化仍然只经过 `scheduler.Manager`。

**改动**

- **服务端**：监听一个 unix socket（`~/.danlu/danlu.sock`，目录 0700，socket 0600），用 `SO_PEERCRED` 确认对方的 uid 和 danlu 相同。之后把请求交给同一套 `/api` 路由，身份记为"命令行"，审计日志照记。这部分是 Linux 专用，放在 `*_linux.go`。
- **CLI**：子命令就是这个 socket 上的普通 HTTP 客户端，请求和响应格式和 `/api` 一样。
- **文档**：README 加一段 rsync + submit 的示例脚本。

**是否做**：取决于你平时会不会从终端或脚本发任务 ❓。

### 5.2 GPU 保留

**问题**：在网页终端或 SSH 里临时调试时（跑一小段代码、测一下显存），调试进程在跑的时候，卡会被当成外部进程跳过，这没问题。但两次调试之间卡是空的，排队的任务会马上占上，下一次调试就 OOM。

**怎么用**

- 首页 GPU 卡片的菜单里有"保留这张卡"，可以选 1 小时、3 小时或"直到取消"，还可以写一句用途。
- 保留中的卡显示"已保留到 15:30"，到期自动释放。
- 排队任务在等这张卡时，等待原因写成"GPU 2 已保留（到 15:30）"。

**改动**

- **状态**：存在 `settings` 表里（运行时状态，不写配置文件）。
- **调度**：`schedule` 把保留中的卡当成忙卡；`allocationWait` 补上对应的等待原因。
- **接口**：`POST /api/gpus/{index}/reserve`。
- 不推送。

### 5.3 其他候选

| 功能 | 做法要点 | 为什么往后放 |
|---|---|---|
| 依赖（`--after`） | 排队任务等指定任务成功后才参与调度；依赖失败时自动取消并写明原因；等待依赖的任务不挡队首 | 只有"训练 → 评测"这类流水线才需要；在那之前，可以先用 3.2 的暂缓手动顶上 |
| 自动重试 | 只针对 `fail_kind = nccl` 这类偶发错误，最多 1 次；重试是一个新任务，`rerun_of` 指向原任务 | 失败分类还没用真机日志校准过，现在按分类重试，容易把真问题盖住 |
| 时长上限 | 提交时可选"超过 N 小时自动取消"，结束原因写"超过时长上限" | 2.3 的静默提醒覆盖了主要风险，先看提醒够不够用 |
| 抓取调用栈 | 在 2.3 的提示里加"抓取调用栈"，对任务进程运行 `py-spy dump`，在手机上就能看到卡在哪一行 | 需要环境里装有 py-spy。Ubuntu 默认 `kernel.yama.ptrace_scope = 1`，只允许祖先进程附加，而 danlu 另起的 py-spy 不是训练进程的祖先，通常没有权限，要把它调成 0 或用 sudo。可以先让 `danlu doctor` 检查这两项 |

## 6. 暂不建议做

- **NaN / loss 告警**：要靠匹配日志文字，各家代码的打印格式不一样，误报多；W&B / SwanLab 本来就做这件事。
- **预计开始时间**：要把排在前面的每个任务的 tqdm 剩余时间叠起来算，误差大。2–3 台机器的单人场景，用处不大。
- **PWA**：起始页面在没有门禁 cookie 时是空白的 404，本地 CA 下 service worker 也容易出问题，换来的只是一个桌面图标。用 Chrome 的"添加到主屏幕"建一个快捷方式就够了。
- **事件流 `/api/events`**：面板轮询的负担不大，真正受益的是桌面客户端，等 C3 时一起做。
- **DuckDNS 证书**：P1 第 5 条改成通过 SSH 获取 CA 之后，它剩下的主要是"新设备不用装 CA"这点方便，等需要时再做。
