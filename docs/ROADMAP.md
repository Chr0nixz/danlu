## 1. 为什么先做后端和面板

- **最大的风险在后端，而且还没验证。** 所有功能都只在 WSL 里用假 GPU 跑过。torchrun 的取消、重启后接管、`KillMode=process`、真实的 `nvidia-smi` 输出，在真机上一旦出问题，多半要改接口或数据模型。客户端做得越多，每次改接口要跟着改的地方就越多：`packages/core`、面板、客户端界面，还有 Rust 层的轮询和通知判断。
- **客户端剩下的 C3 要等服务器稳定。** 部署新服务器、机器体检、自动更新、安装包自带服务器程序、统一版本号，都是围着服务器做的。服务器还在频繁变动时就搭发布流程，做了也要返工。
- **在面板上迭代最快。** 不用安装，手机也能用，构建完马上能看到效果。只有 2–3 台服务器，开几个浏览器标签页也够用。
- **客户端停下来损失小。** C1、C2 已经能用。SSH 那一侧本来就没有端到端跑过，等后端稳定后在真机上一起验证更划算。

## 2. 这个阶段的规则

- **面板是主力界面。** 电脑和手机上都用它，设计和取舍都按主力界面来，不再当成兜底（[PRODUCT.md](../PRODUCT.md)）。
- **面板仍然只管一台服务器。** 不加切换服务器或多台汇总的视图，服务器之间也不组网。每台服务器的安全入口、会话和 CA 都是独立的，在浏览器里跨服务器操作会很别扭。多台汇总仍然是客户端的事。
- **客户端只停新功能，不停编译。** 改 `/api` 时照旧同步 `packages/core`，并保持 `desktop` 的 `pnpm typecheck` 和 `cargo test` 通过。客户端用到的接口变了，只做让它继续能用的最小改动。
- **通知改由服务器自己发。** 客户端停着，任务失败就没人提醒，所以 ntfy 手机推送提前到这个阶段（第 4 节）。

## 3. 目标

一句话：**除了用 rsync 同步代码，一个月都不用为训练任务 SSH 上服务器；手里的任何一个结果，都能在一分钟内说清楚它是怎么跑出来的，并且能原样再跑一次。**

用下面几个场景验收，都要在真实服务器上跑顺：

1. **早上看手机。** 一屏看到昨晚的 6 个任务：4 个成功；1 个失败，原因直接写着"CUDA 显存不足"，而不是"退出码 1"；1 个还在跑，写着跑到第几个 epoch、还要多久。
2. **改了再跑。** 点开失败的任务，把 batch size 改小重跑，在手机上 30 秒内完成。
3. **排了一批。** 晚上排 10 个任务扫学习率，第一个因为参数拼错 20 秒就挂了。队列自动暂停，手机只收到一条通知，不会到早上才发现 10 个全挂了。
4. **两个月后写论文。** 手里只有一个 checkpoint 路径。从路径找到任务，看到当时的 commit、未提交的改动、完整命令、conda 环境里的包版本、显卡型号和驱动；和效果最好的那次对比，代码、参数、环境的差异一屏看清；点"用当时的代码重跑"就能复现。
5. **出了意外。** 服务器断电重启、danlu 被 OOM killer 杀掉、磁盘写满、`nvidia-smi` 卡住。不管哪种，任务状态都不撒谎：能接管的接管回来，跑不下去的标上"服务器重启，任务中断"这类明确的原因，队列照常调度。
6. **在手机上临时处理点事。** 在外面发现某个任务不对劲，在手机上打开这个任务目录的终端，看一眼文件、杀掉一个残留进程，不用找电脑。

## 5. 理想线

定版之后慢慢做，客户端做完以后也可以继续。没有先后顺序。

- **队列**：优先级或"允许插队"开关、hold/release、拖动排序、修改排队中的任务、依赖（`--after`）；自动重试，只用于 NCCL 超时这类偶发错误（DESIGN.md 第 5.3 节）。
- **参数扫描**：一个命令模板加几组取值，生成一批任务，在列表里归成一组。
- **预计开始时间**：根据运行中任务的剩余时间，估计排队的任务什么时候能开始。
- **资源画像**：每个任务记下平均 GPU 利用率和峰值显存，下次选卡数和 batch size 时有依据。这是汇总数字，不是训练曲线。
- **输出文件**：浏览任务的输出目录，预览图片、文本、JSON 和 CSV，生成的样例和评测结果在手机上也能看。
- **任务备注**：给任务写一句话，比如"lr 太大，发散了"。
- **告警**：NaN、卡死、任务结束后卡上残留显存（脏卡）（DESIGN.md 第 5.4、5.6 节）。
- **PWA**：面板可以装到手机桌面。
- **事件流**：`/api/events` 推送任务状态变化，面板和客户端都不用再轮询（CLIENT.md 第 8 节）。
- **受信任的证书**：DuckDNS 免费子域名（第 7.1 节）。
- 其他备选见 DESIGN.md。

## 7. 新设计的要点

### 7.1 证书：零成本，配置尽量少

只保留三种模式：

- **本地 CA（默认）**：零成本，服务器端不用配置。CA 带 NameConstraints，只能给这台服务器的 IP 签证书，装到手机上也不怕私钥泄露后被拿去冒充别的网站。麻烦都在设备那一侧，所以做两件事：
  - `danlu init` 和 `danlu info` 在终端里打印一个二维码，手机扫一下就能打开带安全入口的地址，不用手敲；
  - 设置页按平台写清楚装 CA 的步骤，下载按钮放在显眼的位置。
  - 首次接入和换 CA 时，CA 经 SSH 取回（`danlu ca`），装好再登录，不跳过证书警告：否则能拦截连接的人可以冒充面板拿到密码、换掉下载的 CA（REVIEW-2026-11-04 P1 第 5 条）。

  2–3 台服务器，每台设备一共装两三次。
- **DuckDNS（可选，理想线）**：用免费子域名换一张受信任的证书，设备上什么都不用装。
  - 走 DNS-01 验证，不需要多开端口，随机端口照常用。证书有效期几十天，到期前很早就开始续期，续期失败也有几周的余地，ntfy 会提前提醒。
  - 只配两项：子域名和 token。`danlu cert --duckdns` 交互式询问，token 不出现在命令行上。danlu 顺便维护 DuckDNS 的 A 记录，IP 变了也不用管。
  - 两张证书同时用：用域名访问时给 Let's Encrypt 的证书，用 IP 访问时还是本地 CA 的证书（按 SNI 区分）。DuckDNS 出问题时，走 IP 照样能用；桌面客户端继续用 IP 加固定 CA，不受影响。
  - 代价：要注册一个 DuckDNS 账号（用 GitHub 或 Google 登录）；域名会进入公开的证书透明日志，扫描器更容易注意到这台机器，但随机端口、安全入口和密码都还在。
- **`file`**：用自己的证书，给有域名的人。

不做 Let's Encrypt 的 IP 证书。它免费，但不简单：验证只能走 80 或 443 端口，和随机端口冲突；普通用户运行的服务绑不了 1024 以下的端口；很多机房也不开这两个端口；证书只有 6 天有效期，续期连续失败几天，面板就打不开了。

### 7.2 网页终端：简单，主要给手机用

终端功能已按本节落地，接口、配置和面板行为见 [DEMO.md](DEMO.md)。手机输入法、全屏程序及后台切换后的实机体验仍待验证。

提交任务本来就能执行任意命令，所以终端没有带来新的权限。要多处理的是三件事：WebSocket 握手要检查 Origin，防止跨站劫持；会话会长时间开着；打开和关闭要记进审计日志。

- **入口**：一个终端页，用运行 danlu 的账号开登录 shell。任务详情里加一个"在任务目录打开终端"：cd 到工作目录，激活同一个 conda 环境。
- **手机输入**：xterm.js 配合安卓输入法打字不太可靠，所以：
  - 底部放一个普通输入框写命令，中文输入法、粘贴、历史记录都能正常用，按发送才写进终端；
  - 输入框上方放一排按键：Esc、Tab、Ctrl、Alt、方向键，以及 `|`、`~`、`/`、`-`。点一下 Ctrl 会锁定，下一个按键自动带上它；
  - 用 htop、vim 这类全屏程序时，直接在终端里打字；
  - 字号可以调。
- **断线不丢**：手机一切到别的应用，连接就断了。服务器把 shell 保留 15 分钟并缓存最近的输出，回来后自动接上，中间的输出也会补上；超时没回来就结束会话。需要长期保留的话，在终端里开 tmux。同时最多 3 个会话。
- **安全**：
  - 只认已登录的会话，并检查 Origin；
  - 审计日志只记打开和关闭，不记内容；配置里可以整个关掉终端；
  - 终端里的进程不带 `DANLU_JOB_ID`，取消任务时不会被误杀；
  - danlu 重启会断开终端，训练不受影响。
- **实现**：`creack/pty` 和 `coder/websocket` 都是纯 Go，仍然是静态二进制；Linux 专用的部分放进 `*_linux.go`。xterm.js 只在打开终端页时才加载，首页体积不变。终端和日志一样保持深色。
- **客户端不接**：电脑上有真正的 SSH，而且 Rust 层只转发 HTTP 和 SSE。
- **不做**：多标签和分屏、通过终端传文件、录屏回放。

终端还能帮着看出面板缺什么：哪件事总要开终端去做，就说明面板少了那个功能。

## 8. 做到什么程度算完

1. DEMO.md 第 0 节的 7 条完成标准在真实服务器上全部通过。
2. 第 3 节的 6 个场景在真实服务器上都跑顺。
3. 在真实服务器上跑真实的训练至少两周 ❓，期间没有出现需要手动收拾的问题，比如任务丢失、卡没有释放、状态显示错误。
4. 定版线（第 4 节）做完，或者明确挪到理想线。
5. 手机上打开不觉得慢：在 Chrome 的 Fast 4G 节流下，首页 2 秒内能看到 GPU 和任务 ❓。已达标：2026-11-05 在 390px 手机视口下实测，冷启动 0.80 秒；加上 4 倍 CPU 降速是 1.08 秒，热缓存 0.42 秒。测量条件和请求分段记在 `web/DESIGN.md`。真手机在真实网络下的体感随使用补验。
6. 定版：打一个正式版本号，不再是 `dev-<时间>`。构建脚本已改为读取 git tag；正式 tag 和部署待 S5 验收后完成。

## 9. 之后：回到客户端

1. 让客户端跟上定版时的接口。
2. 在真实服务器上端到端验证 SSH 那一侧：添加服务器、升级、服务管理。同时亲眼确认系统通知弹窗和托盘图标的三种状态。
